# opkg port research

Sources read: shallow clones of git.yoctoproject.org/opkg (HEAD 2026-10-13, CMakeLists says 0.10.0+git; last tag v0.9.0), github.com/openwrt/opkg-lede (last commit 2025-11-05), git.yoctoproject.org/opkg-utils (tag 0.7.0), upterm-ports (RULES.md, pkgs/), invisible-island.net/dialog/dialog.html. Paths below are in those clones (scratchpad `o/opkg/...`), not in the repo. Everything about the Amiga side is unverified until a rig run.

## 1. Build deps and toolchain

Build system: CMake (min 3.25), not autotools (opkg/CMakeLists.txt:2). Options at CMakeLists.txt:16-42:

- Required: libarchive (`find_package(LibArchive REQUIRED)`, libopkg/CMakeLists.txt:156). It reads the ar outer and the tar inner (libopkg/opkg_archive.c:513-631). libarchive is already in upterm-ports/pkgs (3.8.9, static, with zlib, bzip2, liblzma, no openssl).
- WITH_XZ (default ON) needs liblzma: present (xz). WITH_BZIP2 default OFF; bzip2 present anyway. lz4 and zstd OFF; not in ports.
- WITH_CURL default ON needs libcurl via pkg-config. There is NO libcurl in upterm-ports: the base ships a curl binary (`net/curl-8.22.0`), not a library. With WITH_CURL=OFF, libopkg/opkg_download_wget.c runs `wget -q -O dest src` through xsystem. No `-L`, so GitHub redirects fail unless the wget name is a shim over `curl -fsSL`. Cleanest: a small patch adding a third backend that execs `curl -fsSL -o`, or a `wget` shim script in the kit. Do not port libcurl (it would also need AmiSSL linking).
- WITH_SSLCURL needs OpenSSL: leave OFF (the curl binary does TLS).
- USE_SOLVER_LIBSOLV default ON needs libsolv (not in ports; CMake, BSD-3, needs zlib). OFF selects the internal solver, which prints a deprecation warning (CMakeLists.txt:36-40). Choose OFF for the first port (no new dependency), accept the warning, revisit if the internal solver is removed. Unverified: that the internal solver still builds and passes the tests in HEAD.
- WITH_GPGME default ON: set OFF. GPG only; the Yocto tree has no usign (opkg_verify.c:87-96 knows only gpg and gpg-asc). The OpenWrt fork opkg-lede has `ENABLE_USIGN` (CMakeLists.txt:15) and `--verify-program` (src/opkg-cl.c:338).
- WITH_ACL, USE_XATTR OFF. WITH_SHA256 (default OFF) must be turned ON: checksums are only MD5 otherwise, and our plan checks sha256.
- Not ncurses, not perl. pkg-config is only used to find libs; the ports build has to supply a cross `pkg-config` path or the `-D*_LIBRARIES` variables by hand.

Needed POSIX calls (grep over libopkg and src):

- Process spawn: `vfork()` + `execvp()` + `waitpid()` in libopkg/xsystem.c:38-60. All of: maintainer scripts, intercept scripts (opkg_cmd.c:231), wget backend. vfork + exec is exactly what upterm-ports RULES.md rule 3 allows ("No fork; vfork + exec"), and ixemul-vtcon/compat/spawn.c says ixemul has no fork() but has vfork. No `fork()` anywhere in opkg, so `check_bin` should pass. One catch: ixemul's vfork child shares the parent's data, and xsystem calls only `execvp` then `_exit`, which is the safe pattern.
- Locking: `lockf(fd, F_TLOCK)` on `lock_file` (opkg_conf.c:673, :693). Check ixemul-vtcon has lockf (my grep of compat/*.c found no lockf or F_TLOCK; unverified whether ixemul's libc provides it). If absent: add to ixemul-vtcon compat per RULES.md rule 2 (a no-op success or a plain lock-file create-exclusive), never a recipe patch.
- Symlinks: only handled when a package contains them (libarchive extracts them; remove path checks `file_is_symlink`). Our packages will ship none, so a missing symlink() is harmless; `lstat` is used.
- No mmap, no flock, no chroot in opkg code. `setenv`/`unsetenv` used (opkg_cmd.c:197-213, pkg.c:1366).
- Regex (xregex.c) uses POSIX regcomp: check ixemul has it (unverified).

Toolchain facts (upterm-ports): bebbo gcc 6.5, ports link `libixcompat.a` from ixemul-vtcon (RULES.md:11-18), staged under PREFIX /UP-Term (mk/common.mk:28). Recipes are `pkgs/<pkg>/recipe.mk` with VERSION/URL/SHA256/LICENSE/DEPS/CONFIGURE/BINS/STACK; libarchive's recipe (pkgs/libarchive/recipe.mk) is the template, but every existing recipe is autotools. A CMake recipe is new work: a cross toolchain file plus a recipe `CONFIGURE_CMD` (git's recipe shows the `_CONFIGURE_CMD` override pattern, pkgs/git/recipe.mk:20). Whether cmake is on the Mac is unchecked. Runtime is plain AmigaOS plus ixemul (programs are ixemul binaries with vfork/exec, not "plain" exec-only).

Open question for opkg: `/bin/sh`. pkg.c:1378 hardcodes `{"/bin/sh","-c",cmd}`. On the Amiga `/bin/sh` must resolve in ixemul to vsh (or a stub). Check how other ports (git, make) call `/bin/sh`: ixemul-vtcon may map it. Alternative: patch opkg to run `sh` via a configurable `maintainer_shell` option.

## 2. .ipk format and maintainer scripts

- The .ipk is an `ar` archive (Debian-style) or a gzipped tar: opkg_archive.c:513-529 enables both ar and tar formats on the outer layer, with gzip filter. Members: `debian-binary` (text "2.0"), `control.tar.gz`, `data.tar.gz`; inner compression may be gz, xz, bz2, lz4, zstd (opkg_archive.c:568-619). pkg_extract.c errors read "Failed to extract control.tar.*" / "data.tar.*". `opkg-build` in opkg-utils builds them (default outer: tar.gz for compatibility; ar with `-O`; verify in opkg-utils/opkg-build).
- control file (in control.tar): `Package`, `Version`, `Architecture`, `Maintainer`, `Description`, `Depends`, `Section`, `Priority`, `Source`, `Conffiles`, `Installed-Size`, `Provides`, `Replaces`, `Conflicts`. Parsed in libopkg/pkg_parse.c. Control members: `control`, `conffiles`, `preinst`, `postinst`, `prerm`, `postrm`.
- Running scripts: `pkg_run_script` (libopkg/pkg.c:1330-1394): script file path + args via `/bin/sh -c "<path> <args>"` through xsystem. Env set: `PKG_ROOT` = the dest's root_dir (pkg.c:1366). opkg-lede/ipkg also use `IPKG_INSTROOT`; the Yocto version does not set it. Args: `configure` for postinst (opkg_configure.c:40), `remove` for prerm/postrm (opkg_remove.c:271,291). Only the script's exit status matters.
- In offline-root mode (`-o` or `offline_root`), scripts are SKIPPED unless `force_postinstall` (pkg.c:1339-1344). So we must not set offline_root; we want a real dest.
- Could a postinst call `Execute Files/install.dos DEST=...`? Yes in principle: postinst is a shell script run by `/bin/sh -c`; it can call `Execute`. The data.tar content must first land somewhere, then postinst runs `Execute <PKG_ROOT>/.../install.dos`. Caveat from the P10 ledger: vsh's `Execute` handling is being fixed (commit e8baac4e: Execute runs in a Shell of its own so its script runs). A postinst invoked by opkg's vfork + exec of `/bin/sh -c` is a non-interactive context; the same Execute risk applies, so the rig test must call a real package through the real `upkg install`. Preferred: postinst is a vsh/sh script that does what install.dos does (assigns, User-Startup) without nested Execute, if install.dos is already scripted; but the plan said Amiga steps stay in install.dos, so run Execute and prove it on the rig.

## 3. Feeds

- opkg.conf syntax (man/opkg.conf.5.in:39-48): `src/gz <name> <url>` (gzip Packages list; plain `src` is uncompressed), `dest <name> <path>`, `option <name> <value>`, `arch <name> <priority>`. opkg fetches `<url>/Packages.gz` (and `Packages.sig` when `check_signature`), then packages by `Filename` relative to the feed URL.
- Packages fields per package: control fields plus `Filename`, `Size`, `MD5Sum`, `SHA256sum` (parsed at pkg_parse.c:222-278). Built by `opkg-make-index <dir>` from opkg-utils (python script, writes `Packages` and `Packages.gz`; opkg-utils/opkg-make-index:210-215). It needs python3 and `ar`/tar on the Mac, fine because it runs at release time only. `-a` adds the Architecture, `-s` the sha256 (check `--help`; unverified flags). Alternatively `tools/pkgs.py` can write Packages itself since packages.txt is already the table; one writer in Python is simple but duplicates a format, and `opkg-make-index` reading real .ipk files verifies the packages themselves. Recommended: opkg-make-index, driven from tools/pkgs.py.
- Static hosting: `src/gz` needs one base URL where `Packages.gz` and the .ipk sit side by side. GitHub Releases `latest/download/<file>` redirects to objects.githubusercontent.com (302, needs `curl -L`) and works only when the newest release holds ALL feed files (the open question from the upkg plan: one release per base version holding every asset). Releases have a 2 GiB per-asset limit and no per-file count limit that matters; Pages has a 1 GB site soft limit and serves at a stable path without redirects, but a push per release is needed and old .ipk versions need a pruned history. Both work; Releases fits the existing release flow. For `src/gz` the URL would be `https://github.com/spotUP/vtcon/releases/latest/download`, so `Packages.gz` is fetched as `.../latest/download/Packages.gz` and each Filename as `.../latest/download/<Filename>` (flat layout, no subdirectories). Caveat: a base release that does not re-upload an unchanged add-on makes `latest` lose that add-on; every release must re-upload all .ipk files.
- Signatures: Yocto opkg uses gpgme only (needs libgpgme, libgpg-error, libassuan, plus a keyring and `gpg`; not portable here). OpenWrt's fork verifies usign (ed25519, `usign -V -m Packages -p key`, tiny C program with its own ed25519 code, BSD-style licence) through `--verify-program`. For us: skip signatures at first and rely on https plus sha256 in Packages; for later, port usign (a few hundred lines, no deps) and patch Yocto opkg to call it, or base on opkg-lede. Unverified: opkg-lede's `HAVE_USIGN` code path and whether it merges easily into Yocto HEAD.
- Fork choice matters: Yocto opkg is active (cmake, v0.9.0, 2026 commits). opkg-lede is the OpenWrt fork (last commit 2025-11-05; OpenWrt itself moved to apk), so it is the older, quieter line. Recommend Yocto HEAD/v0.9.0 as base.

## 4. Install paths

opkg treats a dest as a unix directory string: `dest root /` gives `root_dir=/`; with offline_root it prefixes (opkg_conf.c:124-148). It calls `opkg_config->offline_root` only for scripts and root prefixing; no device-specific logic. Files extracted by libarchive take the path in the tar entries joined to the dest root (opkg_archive.c:165-250, `join_paths`, `transform_all_paths`).

AmigaOS: ixemul maps `/UP-Term/...` to the volume `UP-Term:` (the ports already install with PREFIX `/UP-Term`, mk/common.mk:28; the configs elsewhere use `/ENV/up-term` for `ENV:up-term`, per ncurses recipe). So: `dest root /UP-Term` (not a device path `UP-Term:`), tar entries relative (`bin/foo`, `share/...`), `PKG_ROOT=/UP-Term`. A device-style dest would break `join_paths`, which treats `/` as separator and `file_exists` stat calls. Prefer the unix form and rely on ixemul's translation. State: `info_dir`, `status_file`, `lists_dir`, `lock_file`, tmp dir all configurable in opkg.conf (opkg_conf.c:54-57), so set them under `/UP-Term/pkg/opkg/...` and `/T` (ixemul maps /T to T:, unverified; use `/tmp` only if ixemul provides it). Files that must live elsewhere (ENVARC:, LIBS:, C:) cannot be a second dest cleanly: the postinst (`Execute install.dos`) does those with assigns, as the owner decided. Needs a rig check that opkg's `mkdir -p`-style creation, `rename`, `unlink` and `lstat` behave on these paths (for example case-insensitive names, no trailing-slash lstat).

## 5. dialog

- invisible-island.net/dialog: LGPL (relicensed from GPL 2005), curses widgets over ncurses; configure flags `--with-ncursesw`, `--enable-widec`, `--disable-extras`, `--enable-nls`, `--enable-whiptail` (page documents "dialog 1.2"; the current release number was not on the page, check the dist archive). Sizes quoted: 171075 bytes for the program with all widgets, 90801 with `--disable-extras` (the page's unit is unclear; counts including libs about 2.3 MB). ncurses (wide) is already in ports, and the terminfo is the kit's. Output goes to stderr by default; `--stdout` and `--output-fd` exist. dialog needs a working terminal in the UP-Term window, which vsh/UP-Term provide.
- debconf: its frontends are Perl (Debian's Dialog/Readline). `perl` exists in upterm-ports/pkgs, but running real debconf is heavy and unproven on the Amiga. cdebconf (C, used in Debian Installer) exists but is big and not a drop-in. Lighter route: our own tiny shell wrapper, e.g. `upkg-ask <questions-file>`, where the question file is a simple line format (`key|type|prompt|default|choices`), each question becomes one `dialog --inputbox/--yesno/--menu/--checklist` call, and the answers are written to a shell-sourceable `answers` file read by postinst; when `dialog` is missing the same file feeds plain `read` prompts (the owner's fallback). whiptail is newt-based (needs libnewt, popt, slang) so it is not lighter than dialog for us. Recommendation: dialog + a 100-line wrapper; skip debconf.

## 6. GPL-2.0 rebrand obligations

opkg is GPL-2.0-or-later (headers say "either version 2 of the License, or (at your option) any later version", e.g. opkg_conf.c:14). Rebranding the binary as `upkg` is allowed. Obligations: keep every copyright and licence notice in the source files; ship the licence text (Files/licenses, as the owner already decided); give the corresponding source of our modified version (UP-Term-src) with the binary release, with offer or inclusion; mark changed files as changed with dates (GPL-2.0 section 2a); license any modifications under GPL-2.0 too; do not remove warranty disclaimers; `upkg --version` saying "based on opkg" is good practice. Linking: libarchive (BSD), liblzma (public domain), zlib are compatible. dialog is LGPL and runs as a separate program, so its obligations are only attribution and source for dialog itself. Trademark: "opkg" is a name, not a registered mark known to me; a new name avoids any confusion. This is not legal advice.

## 7. Recommended phases and risk

P10.1 Probe the foundations (no opkg yet): rig check that ixemul provides `/bin/sh` (or what resolves), `lockf`, `regcomp`, `vfork`+`execvp` of an ixemul binary, and that `dest /UP-Term` style paths work for mkdir/rename/lstat. Done-check: a probe binary run on rig 2 (060) prints a pass line for each, results written in the ledger. Fix any gap in ixemul-vtcon compat, not in recipes.

P10.2 CMake support in upterm-ports plus the opkg recipe (`pkgs/opkg`): cross toolchain file, WITH_CURL=OFF, WITH_GPGME=OFF, WITH_SHA256=ON, USE_SOLVER_LIBSOLV=OFF, libarchive/xz/zlib from the sysroot. Done-check: `make opkg` ends in `check_bin` green (no fork, 68020 scan), `make host-opkg` builds on the Mac, `opkg --version` runs on rig 2.

P10.3 Download backend and rebrand patch: backend that runs `curl -fsSL -o` (or a wget shim), binary renamed `upkg`, config path `UP-Term:etc/upkg.conf`, version string "based on opkg", changed files marked. Done-check: `upkg update` against an https feed served by the Mac fixture (existing fixture pattern, tools/claude_fixture.py) fetches `Packages.gz`; the real GitHub URL gets tested in P10.7.

P10.4 ipk build and feed tooling in vtcon: `tools/pkgs.py` builds one .ipk per package (data.tar from the existing archive layout, control with Version and Depends, `postinst`/`prerm` that call `Execute` of the package's install/uninstall script), runs `opkg-make-index`, and writes the sha256. Done-check: host test that Packages.gz versions equal dist/packages.txt and the sha256 equals each file.

P10.5 Rig end-to-end of install/remove/upgrade: `upkg install UP-Term-nvim` from a vsh prompt on a base-only install, then `upkg upgrade` after a version bump, `upkg remove`. Done-check: record/status file shows the version, `nvim --version` runs, remove leaves nothing; the postinst `Execute install.dos` ran (sentinel in the install record). This is the single reachability test; the rest stays at unit level.

P10.6 dialog port and question wrapper: `pkgs/dialog` recipe (ncursesw, `--disable-extras`), `upkg-ask`, a question file in one real package. Done-check: rig run of an install whose questions are answered via dialog (keys sent through the rig) and via the plain fallback with dialog removed; the answers reach postinst.

P10.7 Release flow: GitHub Releases feed (`latest/download`), RULES.md release steps include all .ipk plus Packages.gz, Aminet keeps the base .lha. Done-check: owner runs `upkg update` and `upkg install Python3` on the A1200 against the live release (owner test, LIVE).

P10.8 Optional signatures (usign port) and P8/P9 rewiring (update check = `upkg list-upgradable`; slim-base packages become .ipk). Done-check: tamper test refuses a modified Packages.gz.

Biggest risk: the maintainer-script and process model on ixemul, namely `/bin/sh -c` plus a nested `Execute install.dos` under vfork + exec, which is exactly where the current `Execute` bug lived (commit e8baac4e) and where unit tests stub Execute. If `/bin/sh` or `lockf` is missing, or Execute from a non-interactive shell does not run its script, every install fails silently. P10.1 and P10.5 are built to catch it first. Second risk: adding CMake to an autotools-only port framework. Advisor note: opkg adds no capability beyond what upkg's fetch/checksum/record already does on the rig; the gain is dependency resolution and a standard feed format, at the price of a new toolchain path, a deprecated internal solver, and a GPL source obligation. Owner decision stands; this just records it.
