### What an UP-Term window plus `upkg update` need

- Window: vtcon-handler (L:) + XCON mountlist (system, :183-184), ixemul/ixnet libs (libs), vsh (system :277,283), the mount part. The user's shell is vsh; vsh is also installed as UP-Term:bin/sh (unix :509), which is the `/bin/sh` that opkg's `xsystem` and every maintainer script go through (P patch 0012 default PATH `/UP-Term/bin:/C`; patch 0016 runs `/bin/sh -c ...`).
- Does vsh need userland? vsh itself is a single 236K binary; the rc file `dist/vshrc` and `dist/Install.installer` assume `ls` etc. exist (`install_rig.py:1121 base_whole`: "vsh ls is coreutils"). Not measured: which vsh builtins exist vs externals. Unconfirmed (see Open questions).
- upkg itself: UP-Term:bin/upkg 577K and upkg-ui 290K are in userland/bin (so inside the 28M); downloads exec `curl` by name (P patch 0001: `argv "curl" "-fsSL" "-o"`), so CURL (3.4M) plus AmiSSL 5 are required for any remote feed (`2026-10-21_upkg-upgrade-base.md` section 4). opkg links libarchive statically (P opkg/recipe.mk:36: DEPS ixcompat zlib bzip2 xz libarchive), so upkg needs no external tar/gzip to unpack an ipk.
- The maintainer scripts the ipks carry do need userland: preinst uses `awk`, `head`, `[ ]`, `echo`, a shell function (V/tools/pkgs.py:~170-186); postinst uses `rm -rf`, `Execute`, `. file`, `set --`; prerm `Execute`, `echo`. So awk (169K), head, rm (coreutils) must be in the bootstrap, as must vsh-as-sh. `upkg-ask` uses `sed`, `$(cat ...)`, `rm`; `upkg-browse` is a vsh script (V/dist/upkg-browse:46 needs upkg-ui; my grep for external commands in it found none besides what upkg-ask uses; grep is a spelling check only).
- So the minimum for "window + upkg update": handler+XCON, libs, vsh (+sh copy), mount, upkg, upkg-ui, upkg.conf and MakeDir UP-Term:pkg/upkg/*, curl + AmiSSL, and the small set of coreutils/awk the scripts call. `UP-Term:UP-Term.version` and `VERSIONS` (tools part) are read by preinst (`head -n 1 UP-Term:VERSIONS | awk '{print $2}'`, pkgs.py:~175) and by `dist/common/check.dos` (Version FILE UP-Term:UP-Term.version): both belong in the bootstrap.

## 2. How add-on ipks are built today

- Table: `V/dist/packages.txt` (29 lines). Columns: id, archive, version, needs-base, ixemul, record, handed, consumes, split on 2+ spaces, "-" empty (header comment at top; parser `V/tools/pkgs.py:22 parse`). Rows today: base, claude, pi, nvim, python, git, perl, vim.
- `addons()` = every row whose `record` is not `UP-Term:` (pkgs.py:145-148): the base row is excluded by construction (docstring cites owner 2026-10-19).
- Make: `V/Makefile:1186` `dist-ipk: dist-claude dist-pi dist-nvim dist-python dist-git dist-perl dist-vim` then `python3 tools/pkgs.py ipk $(BUILD)` and `pkgs.py feed $(BUILD)` (Packages, Packages.gz in build/ipk). `dist:` (Makefile:1057) does not run dist-ipk. `dist-check` (Makefile:1200-1222) ends with `IPK_REQUIRE=1 python3 tests/test_dist_ipk.py`.
- ipk layout (`build_ipk`, pkgs.py:288-306): `debian-binary`, `control.tar.gz`, `data.tar.gz` in an ar. control fields: Package (= archive name, e.g. up-nvim), Version, Architecture (ARCH), Maintainer, Installed-Size, Description (SUMMARY table, pkgs.py:~133-141), plus Replaces/Conflicts/Provides from package-renames.txt (`_rename_fields`, :278-285). NO Depends, NO Section, NO Priority. The feed stanza (:330-335) adds Filename, Size, SHA256sum.
- Control scripts (`_scripts`, :151-192): `preinst` only when needs-base is not "-" (refuses when base < needs-base, reading `UP-Term:VERSIONS` line 1 field 2); `postinst` = `Execute T:upkg-stage/<archive>/Files/install.dos T:upkg-stage/<archive>/Files [KEY "$KEY"...]` then `rm -rf` the stage, with answers from `UP-Term:bin/upkg-ask` when the archive has `Files/questions`; `prerm` = `Execute <record>/Uninstall` (warns and continues if the copy is missing).
- Data staging: data.tar paths `./T/upkg-stage/<archive>/...` (pkgs.py:128-132, 220-245): upkg.conf `dest root /` and ixemul reads /T/x as T:x, so files land in RAM (T:) and postinst copies them via the archive's own install.dos. The ipk therefore carries the whole Files/ tree of the add-on archive, not final paths.
- Could a base part be an ipk with this machinery? Yes for anything whose install is a self-contained `install.dos` run: the ipk is just "the archive's staged kit + postinst Execute install.dos". Gaps for base parts (tmux, unifont, emoji, net, coreutils):
  - install.dos of the base is one script with Labs, not one per part; it takes `STEP`, so postinst could call `install.dos STEP <part>` with ENV:UPTOPT* (as the Installer does, install.dos:28-100), but no such ipk generator exists. An archive row per part would each need its own `Files/install.dos`, `Uninstall`, `VERSIONS`, `MANIFEST` (dist-check Makefile:1207 requires them for every archive in `pkgs.py archives`) and a record drawer.
  - Cross-part state: User-Startup blocks and Assigns (GG:, TMP:, UP-Term: assign, tmux needs ENVARC:tmux.conf and ENV: copy, :293-295); fonts need FONTS: and ENVARC:up-term/font-* markers (:471-495); libs need LIBS: with `.orig` and ENV:upixemul logic (:692-746); handler needs L: and DEVS:DOSDrivers plus a mount (:183-186, 764-772); device needs a boot-block write via UPConsole (:862). All of those are install.dos logic, not data; an ipk can only run them through postinst scripts. ipk data is staged under T:, so there is no direct "install to LIBS:/L:/FONTS:" in data.tar; the copy is always postinst.
  - No Depends field: upkg's solver cannot order "needs tmux" or "needs curl" today (no Depends emitted at all; needs-base is a preinst check against UP-Term:VERSIONS). Offline default-package installs would need either Depends or an explicit order in the full archive's script.
  - needs-base uses the base version in `UP-Term:VERSIONS`; if the base's own parts become ipks the version check would need a new reference (the bootstrap's VERSIONS line).
  - `record` column semantic (UP-Term:pkg/<archive> vs ENVARC:upkg/<archive>) exists for add-ons, MANIFEST per part is possible (D3).
  - mkmanifest/`handed` already model "paths the base hands to an archive" (packages.txt `handed` column; kit-split D7), so moving tmux/unifont/emoji out of the base is a `handed` plus parts.txt move, same as nvim/python did. This is the precedent mechanism for the 1.5 to split migration.

## 3. Offline install

- Upstream opkg 0.9.0 supports it, nothing in upkg's patches removes it. Read in `P/build/src/opkg/libopkg/opkg_download.c`: `opkg_download_cache`/`opkg_download` handle `src` starting with `file:` by `opkg_download_file(src+5, dest)` (a file copy), :136-140, before the curl backend is reached; so a `src/gz name file:/Vol/dir` feed does not run curl. `opkg_prepare_url_for_install` (:481) accepts a remote URL first, then a package name from the lists, then (further down, after the name heuristic) a local file path; `opkg.c:210` and `opkg_cmd.c:441` use it for `install`. So `upkg install /Vol/dir/x.ipk` (ixemul path syntax, `/Volume/...`) and a file: feed are both upstream paths.
- P/pkgs/opkg/patches/: only 0001 touches `opkg_download_backend` (wget to curl, :125-175 of the patch); `grep 'file:'` of all 16 patches finds no hit besides unrelated comments. Patches 0003/0004/0007 (30-character cache names, short temp names) apply to files downloaded into cache_dir; a local `install /path/x.ipk` path avoids the cache but the extraction still uses the `unpack.XXXXXX` short temp names (0007).
- Not verified on an Amiga: a file: feed with Packages.gz via `upkg update`, local-file install, FFS name-length behaviour for a feed with long ipk names (ipk names like `up-nvim_1.0_m68k-amigaos.ipk`? see `ipk_name`, pkgs.py:255; not read). Dependency resolution against a local file also not checked (there are no Depends anyway).
- Staging cost: the ipk data goes to T: (RAM) before postinst copies it (pkgs.py:128). A full archive that installs many ipks offline stages each in RAM one at a time (postinst removes its stage), so the largest ipk (nvim, python) bounds RAM use; sizes of the built ipks not measured here.

## 4. Update and Uninstall records (kit-split D3, D6, D7)

Plan: `V/thoughts/shared/plans/2026-10-13-kit-split.md` D3 :202-211, D6 :287-, D7 :318-360. Line 12 there is answer 1 "Userland: whole in the base."

- D3 (:202-211): base keeps `UP-Term:MANIFEST`, `UP-Term:VERSIONS`, `ENVARC:up-term/opts`, plus `UP-Term:UP-Term.version` (`$VER: UP-Term 1.5 (21.10.2026)`) for add-on base checks, plus `UP-Term:pkg/legacy/{MANIFEST,VERSIONS}` when installed over the single kit. Add-ons keep their record drawer (MANIFEST, VERSIONS, opts/, copy of Uninstall) at the `record` column path; standalone ones at ENVARC:upkg/<archive>.
- MANIFEST format (observed): lines `<size> <crc> Files/<path>`; `handed 0 00000000 handed#Files/nvim` lines mark handed paths (D7.1). One part name per line via mkmanifest from parts.txt. `V/build/dist/up-term/Files/MANIFEST` is 76K for the base.
- Update: `dist/common/update.installer:1-61`: `Files/upupdate <old MANIFEST> <new MANIFEST> <drawer>` writes ENV:UPTUPD<part>, UPTUPDKB, UPTVEROLD/NEW, UPTHANDED, T:UPTUPD-<part>; options come from `ENVARC:up-term/opts` (written by the record step, `V/tools/mkinstaller.py` owns the Installer script; I did not find the write in install.dos). upupdate has no ixemul (:5). Part-level granularity: a changed file reruns its part (parts.txt header lines 1-3).
- D6 (:287-): add-on Uninstall from `dist/common/uninstall-addon.dos`; base Uninstall runs every add-on's Uninstall first (generated from packages.txt) while UP-Term: is assigned. `unstartup.sh <name>` removes one named User-Startup block (`;BEGIN UP-Term <name>`..`;END`).
- D7 (:318-360) recognition rule: a base Install over a single kit is recognised by the OLD `UP-Term:MANIFEST` naming a handed path (`Search UP-Term:MANIFEST " Files/nvim/"`, lab `record` in `dist/common/record-legacy.dos`); it is copied once to `UP-Term:pkg/legacy/`, the new MANIFEST replaces it; `upupdate` skips gone old lines under handed paths (no Delete) and sets UPTHANDED; the Update page then tells which add-ons stay and must be installed as separate archives; an add-on Install with no record but a legacy MANIFEST runs `upupdate legacy new ONLY=<handed>`.
- How a monolithic 1.5 would be recognised for the new split: 1.5 has the same MANIFEST format and `UP-Term:VERSIONS` first line `UP-Term 1.5 de8d662d 2026-10-21 (upterm 0208b9c)`. Same mechanism applies: a new bootstrap row would list `handed` paths (userland tools, tmux, unifont, emoji, net, coreutils, themes ...) and the new MANIFEST carries `handed#` lines; upupdate would skip deleting them. What does NOT exist: a `record` marker telling "this install has the parts that are now ipks", and any code that converts those handed files into package records (upkg's status file at /UP-Term/pkg/upkg/status would not list them). So after migration the files stay but upkg thinks the packages absent; installing the package afterwards copies over (CLONE) the same files; Uninstall of the old install path must still remove them. That "adoption" step is new work. An ipk Uninstall that deletes shared files (e.g. awk) would also break the bootstrap, so bootstrap files must not appear in any package's manifest.
- The 1.5 dev-time rule: `UP-Term:pkg/upkg/...` already exists for upkg state (install.dos:282), so package state sits next to base state.
