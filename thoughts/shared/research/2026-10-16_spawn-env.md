## env to child

### What is ruled out (rig 2, 060, 2026-10-16)

- **spawn.c ignoring envp: no.** coreutils env does not use posix_spawn; `src/env.c:1242` calls `execvp`. spawn.c swaps `environ = envp` in the vfork child; compat/test/spawnprobe already checks envp, and the new envprobe `spawnenv` case passes.
- **setenv not reaching environ: no, not alone.** env uses gnulib's `rpl_putenv`/`rpl_unsetenv` (`build/obj/coreutils/lib/stdlib.h:1708,2527`), which replace the program's `environ` array. ixemul's exec family uses `*u.u_environ` (`stdlib/exec.c:92,141,205`). The new probe `ixemul-vtcon-env/compat/test/envprobe.c` (commit 64389aa on fix/spawn-env) does exactly this gnulib-style replacement and then calls execv or execvp. All 5 ways pass, both from wasabi's exec and from vsh.

### What the rig shows

| started from | command | result |
|---|---|---|
| wasabi `ami.py exec` (one command) | `env FOO=bar VTC:userland/bin/printenv FOO` | `bar`, rc 0 (works) |
| wasabi exec | `env ENVPROBE=a VTC:envprobe child a` | rc 0 (works) |
| `Execute` script, Stack 600000 or 6000 | `env FOO=1 printenv FOO` | rc 2 (fails) |
| vsh script | `env FOO=1 printenv FOO` | rc 2 |
| vsh script | `env FOO=1 printenv` (print everything) | **prints nothing**, rc 2 |
| vsh script | `env FOO=1 printenv HOME` | rc 1: HOME is gone too |
| vsh script | `FOO=1 printenv FOO` (no env) | `1`, rc 0 |
| vsh script | `/VTC/envprobe` | 0 failures |

So under a script or vsh, the child that env execs gets an **empty environment**, not "the environment minus FOO". Stack size makes no difference, so the stack is not the cause.

### Leading hypothesis (unproven, check this first)

The program's `environ` and `*u.u_environ` are different cells:
- crt0 `start_stdio` calls `ix_get_variables(0)`, which passes `environ_out` only `from_vfork_setup_child` (`libsrc/crt0.c:368-383`). Then `environ = env`.
- The library points `u.u_environ` at the stack parameter of `ix_exec_entry` (`library/ix_exec_entry.c:102`), or at `&env` in `_main.c:384`.

gnulib's putenv rebuilds `environ`. ixemul's execvp then sends `*u.u_environ`, which no longer matches. Why the result is EMPTY only when the parent was started from a CLI script or vsh, and fine from wasabi's exec, is not yet explained. envprobe's setter is always spawned, never CLI-started, which is probably why it does not reproduce the failure.

Next probe: add an envprobe mode that runs as the CLI-started process itself (`envprobe direct replace`, with no spawn in between) and prints `environ`, `*u.u_environ` (via `ix_get_vars`/`ix_settings`) and their addresses, run from vsh. If it fails, that mode is the regression test.

Likely root fix: make `u.u_environ` always point at the program's `environ`. That means either crt0 always passes `&environ` as environ_out (an SDK crt0 change plus a relink of every port), or the library learns the program's cell. The second is an ixemul.library change and needs a new library on the rig.

## Root cause (proven 2026-10-16, rig 2, 060)

The environment was never lost. The child's **stdout and stderr were closed** when it started, so printenv's output vanished and its write error gave exit 2.

- `ixemul-vtcon-env/stdlib/execve.c:349-381` (before 387e8df), in `on_real_stack`: on execve, ixemul walked the old image's atexit list and called every handler except stdio's `_cleanup`. The new image then ran in the same user struct, with the same `u_ofile`.
- coreutils registers `atexit (close_stdout)`, which closes fd 1 and fd 2. Every coreutils program that execs (env, nice, nohup, timeout, ...) therefore handed the child closed stdout and stderr.
- Evidence: scratch probe `envprobe2 fds <file>` writes fcntl results for fds 0-2 into a file it opens itself. Exec'd by coreutils env or nice: fd 2 `F_GETFL=-1`, fd 1 is the probe's own fopen'd file (it got the lowest free fd, 1). Exec'd by envprobe2 itself (no close_stdout): fd1 getfl=17, fd2 getfl=18, fine. Same result from vsh, from an Execute script and from the CLI. `env` inside a child ran fine and saw all 14 variables.
- The earlier environ/`u_environ` hypothesis is wrong: every exec combination of ep2 / ep2 with the coreutils stack cookie sees the environment (n=14).
- Open: why wasabi's one-command exec of `env FOO=bar printenv FOO` printed `bar`. Probably wasabi's output channel is not fd 1 / fd 2 as seen through `u_ofile`. Not chased.

## Fix

`ixemul-vtcon-env` 387e8df (branch fix/spawn-env): execve drops the atexit list (`__atexit = 0`) and calls no handler, as POSIX does. The new image registers its own `_cleanup` in `ix_get_vars.c:104`. The only other library-side registration is crt0's profiling `_mcleanup`, which must not run at exec time anyway.

## Regression test

`compat/test/envprobe.c` way `atexit`: the setter registers a handler that closes fd 1 and fd 2, then execs `self child atexit`. The child returns 2 when `fcntl(1|2, F_GETFD) == -1`.
- Before the fix (rig 2, current VTC:ixp6/ixemul.library, from vsh): `[FAIL] atexit: ... (status 2)`, `1 failures`, other 5 ways OK.
- After the fix: NOT RUN. `docker/build.sh` stopped with ENOSPC (263 MB free on /). The library is not built yet.
