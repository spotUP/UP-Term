### Candidate 1 (hook clobbers a register): REFUTED statically
- Stock DrawBox body 0x2450c: `movem.l d2-d3/a3/a6`, leaves only d0/d1/a0/a1 changed. Stock FieldBox body 0x245de
  (stack args): `movem.l d2/a2-a3/a6`. Callers of the bodies: 0x1429c, 0x1d49e (DrawBox), 0x18d68 (FieldBox).
- vbcc hooks (build/amiga/flat_asm/flat.s ~4330-4510): d4_flat_pens, d4_drawbox, d4_fieldbox all `movem` a2-a6/d2-d4
  (every non-scratch register they touch); the flat path's RectFill goes through flat_rf_entry (flat_rf.s), which
  preserves C's callee-saved set. No path leaves d2-d7/a2-a6 changed.
- The only caller that keeps registers live across a hooked call is 0x18d68 (d5/d7/a2/a3 = area inner box), and
  those feed only the area fill RectFills at 0x18f28.., not layout.
- Layout does not read anything a draw writes: a GTCustom_LayoutRel child gets
  `inner = parent_ob->dims + 2` (layout_routines.c:423-438); parent dims are stored at object creation
  (layout_routines.c:925-928) from L_CalcObjectDims, never from a box draw.

### What x=104 means (source-level)
104 = BorderLeft 4 + 12*8 + fine 4 = the window branch of L_CalcObjectDims (layout_routines.c:440-446), i.e.
parent_ob == NULL or WINDOW_OBJECT_PARENT not passed. Equally possible: parent found but its dims.Left == 2
(inner 4 + 96 + 4). Paths that compute a child position: L_AddObjectList (layout_routines.c:893-911, L_GetObject
walks ALL object lists, layout_routines.c:1814-1830) and L_LayoutResize (layout_resize.c:56-90, same lookup; runs
on a window resize). Both find GAD_ENVIRONMENT_EDIT_AREA if it is in the window's list with its id intact.
So the broken state needs either (a) the edit-area GL_Object missing/its id or dims corrupted, or (b) a
LayoutResize against a wrong parent. Neither is a register clobber.

### Stack overflow on the DOpus task (checked, not the cause on frame size alone)
d4 hooks run on DOpus's task without flat_on_stack. Largest vbcc frames in flat.s/flat_core.s: 1128 and 536 bytes
(test_amarchy_frames: 0 over 4096). Depth of the flat chain on the config process not measured.

## Session 6: theme-pick freeze (s66 agent 6) -- source analysis, rig NOT run

Question: why rig 68 (KS 3.2, DOpus on the 640x256x8 Workbench screen, amarchy-flat running) froze in 2 of 3 flat-on runs at the
vantablack pick. Run logs (scratchpad s5-flat2.log:12-18): the Keep requester ("Amarchy") was found once, then gone ("no window titled
'Amarchy'") before the freeze, so the freeze is most likely in the 15 s timeout REVERT (desk_confirm_dos.c:55-67 act -> desk_dos_revert),
which is a second palette reset; the apply itself runs the same steps, so either can hit it.

### Top cause (from source, NOT confirmed on the rig): win_refresh_frames use-after-free on foreign windows
amarchy/win_refresh.c:51-58:
  lock = LockIBase(0); alive = screen_alive(..) && window_alive(..); UnlockIBase(lock);
  if (alive) RefreshWindowFrame(list[i]);
The window is checked under the IBase lock and used after it is dropped. Any window its owner closes in that gap is refreshed after
CloseWindow freed it (Window, RPort, layer): RefreshWindowFrame walks a freed gadget list and locks a freed layer -> hang or crash.
Why it fits every fact:
- Only with flat running: win_refresh_frames is called from dk_flat_sync (desk_dos.c:593) only when the Amarchy.Flat record exists and
  its fields changed (wrote=1). Theme change -> desk_flat_inbar/desk_flat_look change -> it runs, after the apply (desk_dos.c:1231)
  and after the revert (desk_dos.c:1484). Flat held inert by the marker (s5 run 1) still has a record... but its changed set differs; unverified.
- Only with DOpus on the Workbench screen: it walks EVERY window on EVERY screen, DOpus's included. On the Workbench screen DOpus closes and
  reopens its windows around the IPrefs Workbench reset (palette apply / revert), and dopus_theme_send fires "dopus set palette ..." and
  "dopus refresh all" (menu_theme.c:93) without waiting for DOpus; dk_wait_reset only waits for the screen/pens, not for DOpus. On its own
  screen DOpus's windows do not churn with the Workbench reset.
- Intermittent: a timing window between UnlockIBase and RefreshWindowFrame against DOpus's asynchronous close/reopen.
- s5 run 3 ended with no windows at all ("window []") where run 1 had Environment: the window set is churning exactly then.

### Refuted / ranked lower
- flat.c:2344-2349 pens_reap (public screen list, then ObtainSemaphore icl_ss) vs icl_pens_release:943 (icl_ss, then the list): an order
  inversion, but both run only on the amarchy-flat main task; the Text hook (icl_label:1140) only AttemptSemaphore's icl_ss and never takes
  the list. No 2-task cycle in the source. A 3-task cycle (hook holding icl_ss inside ObtainBestPen/ReadPixelArray8 waiting a layer an
  Intuition path holds while it waits the list) would need Intuition internals not shown; not proven.
- flat.c:139 c7_screen_which LockIBase inside a sysiclass draw hook (holds a layer, then IBase = inverted order): reached only when
  GetAttr(SYSIA_Which) fails, i.e. KS 3.1 (flat.c:575). Rig 68 is 3.2. A real latent bug for 3.1, not this freeze.
- Hook stack overflow: would not depend on DOpus's screen.

### Proposed fix (layer: amarchy win_refresh.c, the caller that dereferences windows it does not own)
win_refresh_frames must never touch a window outside a guarantee that it is alive. Do not refresh foreign windows from our task:
refresh only windows whose owner is this process (w->UserPort && w->UserPort->mp_SigTask == FindTask(0)) plus the Workbench's own windows
only when Workbench is idle (desk_dos_wb_ready), and let foreign windows pick up the new flat state on their next own redraw (DOpus already
gets "dopus refresh all" from the theme send). Holding LockIBase across RefreshWindowFrame is NOT the fix: if RefreshWindowFrame
round-trips to input.device on 3.x (unverified) it deadlocks. Also latent: c7_screen_which should read the slot table the main task
fills (as aspect_update does) instead of LockIBase in the hook.

### Regression test idea
Host test (tests/, the win_refresh.c host build with fake Intuition): a fake RefreshWindowFrame that asserts the window is in the screen's
list at call time, and a fake UnlockIBase that removes a foreign window (simulates the owner closing it in the gap); fails on the current
code (refresh of an unlinked window), passes with the owner filter, fails again on revert. Rig A/B (decides it): 4 flat-on picks with a
sentinel counting foreign windows refreshed (AMARCHY_WINREF_FOREIGN), current build vs fix; freeze rate 2/3 -> 0/4.
