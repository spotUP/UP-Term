# FP4.5: is unix-tool-ports row 5.4 covered?

Row 5.4 (plans/2026-10-04-unix-tool-ports.md:208, :350) = "upstream patches (research 2026-10-03): TERM and LANG
from the variables, window size via ACTION_VTCON_GWINSZ and changes". Checked: the 19 patches in
dist/net/bebbossh-1.46.1/patches applied on the 1.45 tarball (scratchpad copy, all 19 apply), the build script
tools/build_bebbossh.sh, vtcon 4ae821c (K6: build from source + 19 patches; no vtcon-specific patch), dist/vshrc.
No device run was possible (no rig): everything below is from source, not from behaviour.

## Covered (evidence)
1. TERM from the variable: COVERED, in 1.45 already. src/bebbossh.cpp:1109 `getenv("TERM")` overrides the
   built-in `xterm-amiga` (:107); research 2026-10-03_ssh-for-up-term.md:34 measured it (local `Set TERM` is read,
   `SetEnv` global is not). UP-Term supplies the value: dist/vshrc `ssh() { TERM=$(remote_term) bebbossh "$@"; }`
   (d24e3b07), remote_term maps vtcon/vtcon-amiga to xterm-256color, UP_REMOTE_TERM overrides; dist/README.txt:664.
   Gap: only vsh's `ssh` function; bebbossh started from an AmigaDOS shell in an XCON window with no local TERM
   still sends xterm-amiga (not a patch item, a usage limit; unverified on a rig).
2. LANG: PARTLY. Patch 0002-charset (src/bebbossh.cpp:486-492) stops sending `LANG=C` for interactive sessions
   (stdout is a console), so the remote keeps its own (UTF-8) locale; scripts/redirected still get LANG=C. That
   removes the 1.45 defect named in research :38. LANG is not read from a local variable, and nothing sends the
   local LANG; row 5.4 wording "from the variables" is not literally met, but the need (remote UTF-8) is.
   RISK, UNVERIFIED: the same patch converts UTF-8 <-> ISO-8859-1 (or the codesets.library system codeset) for
   interactive sessions (consoleWrite :253ff, typed input :757-:780). UP-Term's xterm personality is UTF-8; the
   Amiga personality is Latin-1. In an xterm-personality window the converted output would show e-acute etc. as
   Latin-1 bytes. 1.45 (measured 2026-10-03: "cafe with e-acute" right) had no conversion. Nothing in the repo tests
   this: tests/test_dist_bebbossh.py checks files/patch order; tools/rig/install_rig.py:1388ff checks $VER and usage.
3. Window size at start: NOT via ACTION_VTCON_GWINSZ. src/console.cpp:50-80 `getConsoleSize()` writes `CSI 0 SP q`
   (Amiga "window bounds request") and parses `CSI 1;1;rows;cols r`. vtcon's engine treats `CSI 0 SP q` as
   DECSCUSR (engine/vtengine.c:3675) and grep finds no window-bounds reply (`1;1;`) in engine/ or handler/.
   So the 1.45/1.46.1 client most likely gets no answer: WaitForChar times out (200 ms) and numCols/numRows stay 0
   (pty-req and window-change would send 0x0). Research :41 left this "not yet checked", and research :30 saw
   `stty size` = 35 x 84 on the rig, which contradicts this; the answer to that is not in the repo -- UNVERIFIED,
   needs one rig run (below).
4. Window-size changes: bebbossh.cpp:525 enables `CSI 2;11;12 {` raw events; on `CSI 12;` (bebbossh.cpp:722ff)
   it calls getConsoleSize() and sends window-change (sendWindowResize). vtcon's `{` is DECSERA (vtengine.c:3595,
   :3874), no resize event class 12 is produced (grep of handler/ finds only IDCMP_NEWSIZE handling, no `CSI 12;`
   report). So changes do not reach the remote through bebbossh. (net/uptelnet.c:32,:396 already follows resize via
   ACTION_VTCON_GWINSZ: the working model, W47 rig tools/rig/winch_rig.py for ixemul programs.)

## Remaining patches (new, ours; GPL, go into dist/net/bebbossh-1.46.1/patches as 0020+)
- P-A size: in getConsoleSize() (src/console.cpp, `__AMIGA__`) first try
  `DoPkt(fh->fh_Type, ACTION_VTCON_GWINSZ=0x7657, fh->fh_Arg1, &winsize, ...)` (struct = vt_winsize: ws_row, ws_col,
  ws_xpixel, ws_ypixel, shorts; pattern: net/uptelnet.c:396, proc/top_amiga.c:85), fall back to the CSI query for
  non-vtcon consoles. Also feed the pty-req of bebbossh.cpp:136 and bebboscp.cpp:159 (they read numCols/numRows).
- P-B changes: bebbossh must learn of a resize without the CSI 12 event: poll GWINSZ in eventLoop (client.cpp:1542)
  at its existing wait tick and call sendWindowResize() when it changed; or have vtcon emit `CSI 12;..|` on
  IDCMP_NEWSIZE when `CSI 2;11;12 {` was set (handler change, larger, and `{` is DECSERA in the xterm personality).
  Polling is the small one.
- P-C LANG/charset: in a vtcon window (GWINSZ answered = UTF-8 xterm personality) skip the Latin-1 conversion
  (charsetConv=false) and decide LANG from the local variable LANG (`getenv`), defaulting to the server's own;
  keep conversion for stock consoles. Needs a rig check first to confirm the mojibake (item 2).
- P-D (optional, no patch): vshrc could export TERM for bebbossh from AmigaDOS shells; out of scope for 5.4.
- Rig check to run before writing P-A..P-C (owner/rig agent): in an XCON window, `Set TERM xterm-256color`,
  `bebbossh -i KEY user@mac` then `stty size; echo caf\xc3\xa9` (printf), resize the window, `stty size` again.
  PASS for row 5.4 = size correct at start, correct after resize, accented text correct.

Verdict: 5.4 is NOT covered by K6. Item 1 covered, item 2 half (mojibake risk), items 3 and 4 open. K6 only
rebuilt the fork's patches (none touch TERM/size/events: grep of the 19 patches).

## Missing capture and how to produce it
Same byte stream into both terminals, compare text+attributes (no images):
1. Fix the script: `tools/capture_claude.py` shows the pattern for recording a session to .bin (the engine side
   replays with `build/vtdump <file>.<cols>x<rows>.bin`, tests/streams/ format; the tools/refdiff.py header
   describes the dump fields: text, cursor, colours, bold/inverse/underline).
2. Mac, iTerm2 at the same size (e.g. 80x24, set via a profile or `printf '\e[8;24;80t'`): run
   `script -q /tmp/p7-screen.typescript screen` and do the P7 steps (split, scroll, a chat log via `yes | head -200`
   style output with `sleep`), exit. Replay the typescript into iTerm2 with `cat` after `reset` and read the cells
   with iTerm2's Python API (`iterm2.Session.async_get_screen_contents()`, per line `string` and
   `style_at(x)`) writing a text dump; same for tmux (`script ... tmux`).
3. vtcon side: `build/vtdump` on the same typescript (host engine) for the engine cells, and on the rig
   `tools/rig/vttest_rig.py`-style capture (or `screen_rig.py`/`tmux_rig.py` plus a cell dump through the
   handler's debug dump) for the Amiga cells.
4. Diff the two text dumps cell by cell (script: extend tools/refdiff.py with an `iterm` reference column).
Caveat: iTerm2 and the engine legitimately differ on things the owner decides (fonts, bold-as-bright, cursor, theme
colours), so the colour columns need a mapping before "differs" means anything. The verdict "good enough" is the
owner's. I read no image.
