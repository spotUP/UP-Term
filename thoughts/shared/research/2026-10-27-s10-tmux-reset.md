## r2 launcher probe (rig 7, 2026-10-27; no product change)

- A. Control through Amarchy, case_run_editor (Apps > Editor, run:nvim): 1 -> 1, nvim process and UP-Term window exist. NO reset. A run: row through run_in_uterm is fine.
- B. tools-less probe (scratchpad ltprobe.c: Open XCON:0/20/640/300/UP-Term/CLOSE, SystemTags `"UP-Term:bin/vsh" -c "tmux"`, SYS_Input w, SYS_Output 0, SYS_Asynch, NP_StackSize 262144, TERM=vtcon set) from wasabid: 1 -> 1, `tmux ls` = "0: 1 windows (attached)", tmux stays up. The reset happens inside the tmux task's startup (after ixemul open), not in Amarchy's code.
- C. Not run (budget): stack 65536 vs 262144 and `tmux -V` variants.

Verdict: tmux's startup resets the CPU, but only when launched from the amarchy-gui process; the identical SystemTags launch from wasabid does not. So not the launch tags/stack 262144 alone, and not run_in_uterm in general (A clean). Remaining difference is the launcher's context (amarchy-gui's cwd/path/pr_* inheritance, an open menu, console/screen state, or the window on the front custom screen). Unknown which.
Next: launch tmux from amarchy-gui's context with `tmux -V` / `tmux new -d` via a temporary ENV keymap row to see if any tmux runs resets there, and run the ltprobe from a process started by amarchy-gui (e.g. a run: row `ltprobe 262144 ...`) to separate parent context from the menu being open.
