## r5 setup diff (rig 7, 2026-10-27; no product change)

Verdict: the one thing `--setup` does that stops the reset is that it Breaks the BOOT-STARTED Amarchy (Process 5, `Run >NIL: UP-Term:bin/Amarchy` from User-Startup, pri 0, stack 4096) and starts a fresh Amarchy by hand. Apps > Tmux resets only while the boot-started instance is the one serving the menu. Binaries, the UP-Term: assign, fonts, env and the Amarchy stack are not the cause. Root mechanism inside that instance: NOT found.

`--setup` changes (amarchy_gui_rig.py setup(), line 1060): (1) Break every process whose Status line has UP-Term:bin/ or VTCX:Apps/bin (kills the boot Amarchy); (2) Copy kit UP-Term/bin to VTCX:Apps/bin; (3) put build Amarchy, amarchy-menu, amarchy-gui there; (4) Assign UP-Term: VTCX:Apps; (5) Assign UP-Term: kit ADD; (6) Run >NIL: VTCX:Apps/bin/Amarchy (fresh instance). Main() then also does stage_build + stage_fonts (FONTS: ADD) in both flows.

Results (plain `rig.py install` + `start --max`, then r5drv; "Reset at" count in build/rig7/logs/fs-uae.log.txt; harness scratchpad bis.sh, fresh boot per row):

## r6 boot instance (rig 7, 2026-10-27; no product change)

Verdict: the console and handle hypothesis is REFUTED, and no static property of the boot instance reproduces the reset. A hand-started Amarchy that has the boot instance's stack (4096), priority (0), cwd (SYS:), empty AmigaDOS path (Path RESET) and a parent console that ended (EndCLI >NIL:) still gives 1 -> 1. Worse for any "inherited value" theory: with `wasabi snoop` attached (DOS call patches, slower) the UNTOUCHED boot-started Amarchy also gave 1 -> 1 with the menu and vsh -c tmux running. So the reset is timing-dependent (race or load), not a property the boot instance holds.

| row | setup (fresh boot each) | resets | notes |
| p1 / p1b | Break 5; NewShell CON: FROM script {Run >NIL: Amarchy; EndCLI} | 1 -> 1, tmux ok | Amarchy came up stk 16384 pri 1 (inherits wasabid), so not boot-like |
| p5 | Break 5; script {Path RESET; Stack 4096; CD SYS:; ChangeTaskPri 0; Run >NIL: Amarchy; Wait 3; EndCLI >NIL:} | 1 -> 1, tmux ok | Status FULL: stk 4096 pri 0 = identical to boot Process 5 |
| snoop | NO change: boot Amarchy, `wasabi --host 127.0.0.1 snoop` streaming during r5drv | 1 -> 1, tmux started (snoop log lines 252-264: tmux LoadSeg ok) | plain boot without snoop: 1 -> 63/69 (r5) |

Probe 4 (code read, cited): amarchy/leaf.c:75 run_in_uterm does `SystemTags(line, SYS_Input, w, SYS_Output, 0, SYS_Asynch, TRUE, NP_StackSize, ...)`. SYS_Output 0 and no NP_Path/NP_CurrentDir/NP_ConsoleTask: the child inherits the caller's Output, path list and cwd. The window w is opened fresh by Open(spec) at leaf.c:68, so input is never the boot console. upassign_vsh() (config/upassign.h:120) looks the vsh path up on every call (Lock with pr_WindowPtr = -1), nothing cached. termenv_ensure (amarchy/termenv.c:9) reads/sets the GLOBAL TERM each call. Nothing in the spawn path carries a boot-console handle.

Boot context for the record: S:User-Startup (Executed from Startup-Sequence, which ends EndCLI >NIL:) runs `Run >NIL: UP-Term:bin/Amarchy` then amarchy-index; boot Process table: 1,2 wasabid, 3,4 upgetty (stk 4096 / 262144), 5 Amarchy, 6 Status, 7 DO_LAUNCHER.

(1) Reproduce the plain boot, then in the SAME run have wasabid `Break 5` AFTER r5drv's reset to see nothing; instead capture the guru: Stack-first rule (feedback-amiga-stack-always): run the plain-boot flow with a startup `Stack 262144` in User-Startup before the Amarchy Run (the boot Amarchy gets 4096 and its children inherit via SystemTags only where NP_StackSize is not set; the vsh child path sets 65536 via pl_stack, but the tmux process and other Run/System chains inherit the 4096 CLI default). Hand Run at 4096 gave 1 -> 1, which does not support it, so also (2) add `wasabi debug` (KPrintF stream) during the plain boot flow to catch the last lines before the Reset, which snoop's patching hid.
