# s10 tmux reset: launcher vs tmux (rig 3, pg8-text2)

Launch line Amarchy builds (amarchy/leaf.c run_in_uterm): window Open("XCON:0/20/640/300/UP-Term/CLOSE" [/SCREEN name]), then
SystemTags(`"UP-Term:bin/vsh" -c "tmux"`, SYS_Input w, SYS_Output 0, SYS_Asynch, NP_StackSize max(65536, vsh cookie)); termenv_ensure sets global TERM=vtcon if unset.
Keymap: dist/keymap `apps.tmux = Tmux | run:tmux`.

Results (fs-uae log "Reset at" count, baseline 1 = power-on):
1. Plain vsh: `tmux new -d -s probe` rc 0, `tmux ls` rc 0 "probe: 1 windows". Resets 1 -> 1. CLEAN.
2. By hand outside Amarchy: `Run <>XCON:0/20/640/300/UP-Term/CLOSE "UP-Term:bin/vsh" -c "tmux"` (ENV:TERM absent, then Setenv TERM vtcon): Run rc 0, `tmux ls` rc 1 (no server, tmux not running after the window), resets 1 -> 1. CLEAN (no reset; note no server either, so this is not an equivalent of SystemTags with NP_StackSize).
3. Through Amarchy (r5drv.py, case_run_tmux): menu opens, Apps row, Tmux row found; clicking Tmux -> wasabi connection refused, resets 1 -> 61 (loop "Reset at 00F80DC8"/"00F800D0"). No Illegal/Exception/Guru line.

First step that resets: opening Apps > Tmux from the running amarchy-gui (step 3). Last output before: "ok run_tmux: the Apps level has a Tmux row".
Not tmux alone (step 1) and not `vsh -c tmux` in an XCON window via Run (step 2). Remaining difference: SystemTags with SYS_Output 0 + NP_StackSize + Open() window on the front screen, from inside amarchy-gui, or the Amarchy process itself (not caught: no wasabi guru possible, the reset is a CPU reset not an exception).
Next probe (new agent): a tiny test program calling the same SystemTags with the same tags (stack 262144, SYS_Output 0, Asynch) outside Amarchy; and run Amarchy with the row's `vsh -c "echo hi"` instead of tmux to see whether any run: row resets (editor row, case_run_editor, is the control).

## r2 launcher probe (rig 7, 2026-10-27; no product change)

Reset count = "Reset at" lines in build/rig7/logs/fs-uae.log.txt (baseline 1 per boot).
- A. Control through Amarchy, case_run_editor (Apps > Editor, run:nvim): 1 -> 1, nvim process and UP-Term window exist. NO reset. A run: row through run_in_uterm is fine.
- B. tools-less probe (scratchpad ltprobe.c: Open XCON:0/20/640/300/UP-Term/CLOSE, SystemTags `"UP-Term:bin/vsh" -c "tmux"`, SYS_Input w, SYS_Output 0, SYS_Asynch, NP_StackSize 262144, TERM=vtcon set) from wasabid: 1 -> 1, `tmux ls` = "0: 1 windows (attached)", tmux stays up. Same on a fresh boot, and again with Amarchy running (menu not open). NO reset.
- Repro: case_run_tmux through amarchy-gui on a fresh boot: 1 -> 59 resets. wasabi snoop's last lines before the stream died: task `tmux` (started under vsh) OpenLibrary bsdsocket v3 ok, usergroup.library fail (Error 205), ixnet.library v44 ok, GetVar UMASK fail, OpenDevice timer ok, ixemul.library v47 ok, "FindTask ... 37 more identical", then "snoop stream closed: connection closed by the Amiga" (22:38:01.107). The reset happens inside the tmux task's startup (after ixemul open), not in Amarchy's code.
- C. Not run (budget): stack 65536 vs 262144 and `tmux -V` variants.

Verdict: tmux's startup resets the CPU, but only when launched from the amarchy-gui process; the identical SystemTags launch from wasabid does not. So not the launch tags/stack 262144 alone, and not run_in_uterm in general (A clean). Remaining difference is the launcher's context (amarchy-gui's cwd/path/pr_* inheritance, an open menu, console/screen state, or the window on the front custom screen). Unknown which.
Next: launch tmux from amarchy-gui's context with `tmux -V` / `tmux new -d` via a temporary ENV keymap row to see if any tmux runs resets there, and run the ltprobe from a process started by amarchy-gui (e.g. a run: row `ltprobe 262144 ...`) to separate parent context from the menu being open.
