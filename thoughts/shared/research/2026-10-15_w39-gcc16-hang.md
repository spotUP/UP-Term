# W39: the gcc 16 string-object hang

## What the hang was

Not a compiler hang on the host. It was ixemul.library built by Bebbo's gcc 16
(`~/opt/amiga16`, m68k-amigaos, 16.1.1b) hanging on the Amiga: every program
hung on its first `memmove()`. The plan line (2026-09-28-vtcon.md:1402 W39 and
:1447 W48) is stale: it records the 2026-10-05 state. The ixemul plan
(`../ixemul-vtcon/thoughts/shared/plans/2026-10-05-ixemul-80-migration.md`,
lines 190-206) records the cause and fix on 2026-10-06.

## Root cause

`string/memmove.c:9` implements `memmove` by calling `bcopy(src0, dst0,
length)`. gcc 4+ treat `bcopy` as a builtin and fold it into `memmove(dst, src,
n)`; inside `memmove` itself that is a call to its own entry. Invariant broken:
a libc function that implements a builtin must not be lowered into that builtin.

Fix (library level, the right one -- the compiler is correct to fold builtins in
ordinary code): `string/Makefile.in` builds with `-fno-builtin` (ixemul-vtcon
45f8bd3, 2026-10-06), plus `libc_impl.h` turning off
`-ftree-loop-distribute-patterns` so loops do not become `memset`/`memcpy`
calls (e8bcc9d).

## Re-test 2026-10-15, host only (current toolchain)

Compiler: `~/opt/amiga16`, cc1 dated 2026-10-05 21:39, i.e. the same binary the
2026-10-06 rig results were taken with. Source: ixemul-vtcon feature/ixemul-80
at 36517d2 (clean). `string/all.c` regenerated in the scratchpad exactly as the
Makefile does (`libc_impl.h` first, sorted sources catenated), compiled with the
build's flags (`-O2 -m68020 -m68881 -fomit-frame-pointer -mfloat-return-d0
-std=gnu89 -fcommon`), with and without `-fno-builtin`:

| build | `_memmove` calls | result |
|---|---|---|
| -O2, no -fno-builtin | `bras d6e <_memmove>` | self-jump: hang |
| -O0, no -fno-builtin | `jsr %pc@(590 <_memmove>)` | self-call: recursion until the stack dies |
| -O2, -fno-builtin (shipped) | `jsr %pc@(a0 <_bcopy>)` | correct |
| -O0, -fno-builtin | `jsr %pc@(a0 <_bcopy>)` | correct |

`tools/selfcall_check.py` on the shipped flags: "[OK] no function branches to
its own entry". The bug reproduces on the host only with the fix removed; with
the shipped flags it does not.

## Rig evidence already on record (not re-run here; host-only task)

ixemul plan 2026-10-06: `ls` and ixc99 17/17 on the full gcc 16 library (before
the fix `ls` hung); after the second fix (stackextend.c dead store, 3ebef54,
8fb9acb) getty_rig 7/7 and R1-R11 pass except R4 colour cube and R7 reflow,
which also fail on 2.95 / 48.2. malloc about 40 percent slower than 2.95.

## Found

- `tools/selfcall_check.py` misses the -O0 form: its regex wants the line to
  end in `<_name>`, and `jsr %pc@(590 <_memmove>)` ends in `>)`. The guard
  also is not wired into any Makefile or test, so it only runs by hand.
  Both are small fixes in ixemul-vtcon (regex `<(_\w+)>\)?\s*$`, and a
  `check` target on the string/stdlib/general archives).
- W39's remaining open work is not this hang: the CPython / neovim rebuild with
  gcc 16 and the size/speed comparison, and the malloc slowdown.
