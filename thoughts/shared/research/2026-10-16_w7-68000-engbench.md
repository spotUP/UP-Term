# 68000 engine speed (W7)

Machine: rig 2 `rig.py start --a500` (FS-UAE A500, 68000 7 MHz cycle-exact, OCS, 8 MB Zorro II fast, KS 40.63; `CPU` reports "System: 68000"). It booted on the second try (the first try printed "no wasabid answer", the built-in retry came up; boot.log showed only "go started"). No rig.py change was needed. Comparison: `rig.py start --a1200` (68020 + 68882, caches on, real speed).

Command: `VTC:engbench<build> ONLY <w> REPS 3` for w = 0..6 (best of 3; time in 1/50 s ticks; rate in bytes/s). 68000 build: `make BUILD=build/a500 CPU=68000 build/a500/amiga/engbench`; 68020 build: `make build/amiga/engbench`.

Why ONLY: plain `engbench` runs the renderer self-check first, and its vp_span_fast (render/painter_68k.s) uses BFINS, a 68020 instruction (the handler checks AttnFlags before calling it; engbench does not). On the 68000 that check takes an illegal-instruction trap and the machine reboots (wasabid vanishes and comes back after the reboot). `ONLY w` skips the checks. Not a vtcon engine fault, but engbench itself cannot run its checks on a 68000 (fixed afterwards: engbench skips the renderer check without AFF_68020 and prints "render asm: skipped (68000)"; `ONLY 9` on the A500 rig: "asm: ok (0)", rc 0, no reboot).

The two A1200 columns are identical tick for tick: the hot loops (vtengine_68k.s) are the same code in both builds and run in the same time. The 68000 build costs nothing on the 68020.

Headline: the A500 68000 engine feeds plain text at 33-45 KB/s (a 9600 baud line is about 1 KB/s, 115200 baud about 11.5 KB/s). Worst workloads: 12000 newlines at 2.4 KB/s (xterm dialect; scrolling) and ins/del line at 4.9 KB/s; ls -l colour 12-19 KB/s. The 68000 is 6.4x to 8.1x slower than the stock A1200 (68020 at 14 MHz with caches). The measurement is the engine alone, no drawing (callbacks draw nothing); the renderer on a 68000 is not covered.
