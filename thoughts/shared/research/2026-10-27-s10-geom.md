# S10 drawn menu geometry drift (host-side analysis, no rig used)

Verdict: the product code and menu_geom.c agree; the rig's expected() inputs are wrong. Both sides call the same
mg_metrics_for / mg_width_t / mg_layout (amarchy/gui.c:1479,1491 vs tools/rig/amarchy_geom.c). No drift commit in
menu_geom.c (last change 5f9d06bb / cda923fb, 2026-10-26). The inputs differ in the FONT.

Evidence
- Host tool amarchy_geom with 640x256, ysize 8 gives root 169,27 h=202 (matches the rig's want y=27 h=202).
- Brute force over ysize 5..16 at 640x256: only ysize 13 gives y=25 h=206 (observed). So the product laid out with a
  13-pixel-high font, not topaz 8. Width 372 is consistent with a wider font too (fixed cw 8 gives 340).
- gui.c:1381 reads ap.val[AM_FONT] (amarchy-menu-font, ENVARC:Amarchy/prefs, introduced 4c48a1a2 2026-10-26) and
  opens mt_open(scr, square, spec) (gui.c:1383). tests/amiga/scrprobe.c:76 measures with menu_font_open(s, square,
  "", 0, ...) i.e. NO preferred font ("the per-screen default choice the menu makes without amarchy-menu-font",
  scrprobe.c:75). tools/rig/amarchy_gui_rig.py probe()/expected() (lines 78-86, 114-) feed that into build_geom.
- The rig never clears/sets amarchy-menu-font (grep: only own_prefs_rig.py writes it, topaz:8/9 variants). A rig
  disk with a menu font in its Amarchy prefs gives exactly this mismatch. UNVERIFIED on the rig: I did not read the
  rig's ENVARC:Amarchy/prefs (host find timed out, rig not started).
- Also note (secondary): case_default uses expected(geom,'-') without wb=True although the rig is OS 3.2 (WORKBENCH
  port exists): the root level then has 11 rows in the product vs 10 in the helper; height unaffected (rows capped),
  width could be (Workbench group label).
