# wasabi 0.8 evaluation (phase 1 of "evaluate, then migrate")

All runs on rig 2 only (`UPTERM_RIG=2`, `rig.py start --max`, 68060, Workbench 640x256 4 bit, Kickstart 40.63),
wasabid 0.8 on port 1235 with the rig key, amiagent 0.13.2 on 7847, both up at once. Rig 2 stopped at the end
(`rig.py stop`, 6 s after the last write). Raw logs: session scratchpad only. Not tested: a real Amiga, TLS,
an RTG (deep) screen grab, a blocking System Request.

## Verdict: replace, with gaps

For what an agent does (commands, files, screen, gadgets, menus, keys, ARexx) wasabi 0.8 does everything amiagent does
that vtcon uses, is faster on exec, and adds menu pick by path, gadget text set, ps/kill/snoop/debug/guru. It cannot
replace `ami.py` as a drop-in: 72 vtcon files import `ami.py`'s Python API (raw frames, raw key codes with
qualifiers, tick-timed input scripts, region grabs, pixel rows), and wasabi's client is a CLI whose coordinates are
in aspect-corrected pixels. Replace amimcp with wasabi_mcp.py: yes, after the gaps below are accepted or patched.
Replace ami.py: only behind a thin adapter (the migration outline says how).

## 2. Build of wasabid 0.8

`make wasabi AMISSL_SDK=<vendor/amissl-5.27/AmiSSL/Developer>` (new pin 68ef646; worktree branch
`feature/wasabi-0.8`): builds with Bebbo gcc 6.5.0b here, 102 KB `wasabid` (0.2 was 55 KB), exit 0.
- `health.c` needs `proto/devicetree.h` and mailbox: shipped in upstream `include/`, no longer a blocker.
- TLS (`tls.c`) is compiled in and needs the AmiSSL 5.27 SDK headers and stubs at build time (the SDK
  `make amiga` already uses); at run time TLS is optional: wasabid on loopback (emulator) spoke plain, no AmiSSL on
  the rig (the README: loopback and emulators need neither AmiSSL nor keys).
- Our shim `tools/rig/wasabi_shim` had to grow: PIXFMT_* codes and LBMI_* tags (cybergraphics.h) and
  `LockBitMapTagList` (-168) / `UnLockBitMap` (-174) inlines (proto/cybergraphics.h) for 0.8's direct deep-screen grab.
  Values are from memory of the CyberGraphX SDK, NOT verified: the grab of an RTG screen was not run (the rig's
  Workbench is PAL 4 bit; `rig.py rtg` + reboot would test it). The 4-bit grab path (ReadPixelArray8) is unaffected.
- The Makefile flags now keep upstream's `-fbbb=-` (Bebbo's loop pass miscompiles small structs, upstream commit
  note) which our 0.2 flags lacked.
- `rig.py wasabi on/off/snoop/ps` and `tools/test_rig_wasabi.py` work unchanged with 0.8 (snoop log showed amiagent's
  own calls, ps listed XCON with stack headroom).

## 6. Gaps, ordered by what they cost

1. No Python API as stable as `ami.py`: the client is one 4040-line CLI file (`Conn`, `do_run` are importable but
   internal). 72 vtcon files need an adapter.
2. No raw key codes and no PgUp/PgDn/Home/End/Insert/F11/F12/keypad names in `key press`; vtcon's scripts use codes
   0x44, 0x42, 0x45, 0x41 and letters (all expressible), so the real loss is small but real for new work.
3. No screenshot region, no pixel-row API (PNG file or `--raw` PNG only; decoding is ours to write; the
   `--raw` PNG matched `ami.grab` exactly on a 4-bit screen).
4. No tick-timed input batch; a drag works through separate calls (tested once, on this fast host).
5. Coordinates: `windows`/`ui list` report grab space (rows doubled on 640x256); `mouse` takes the same space.
   Consistent inside wasabi, different from UITREE; every script with `window(...)['box']` needs the factor.
6. Gadgets by label only (no ids); unlabeled gadgets need `--kind/--nth`.
7. `arexx REXX` needs a quoted program; `arexx AREXX` returns nothing.
8. Direct RTG grab path and its CGX shim constants untested (see 2). A System Request blocking the daemon untested.
9. amiagent's `break` did not work from a second connection ("no command is running"); not a wasabi gap but a
   reason the SKILL.md "a requester blocks amiagent" advice has no tool answer today.
10. Real Amiga: TLS needs AmiSSL 5 + keys (`wasabi keys`); an Amiga without them stays plain; a client that reached an
    Amiga encrypted refuses plain later. Not run here.
11. No pointer position query (0.9b2 PROTOCOL.md: MOUSE only moves/clicks, WINDOWS and INFO carry no pointer
    position). `ami.py` POINTER (0x0B) stays a named gap; its only legacy caller, `pointer_scale()`, uses the
    row scale instead. (BREAK is mapped, WM3b: SLOTS, then FREE with the Ctrl-C-only flag per running slot.)

### Status at wasabi v0.9 (pinned 2026-10-15, d5a57f4; recorded 2026-10-15)

pixels; checked on rig 2 (68060): a move to (200, 200) read back (200, 100), `pointer_scale()` stays (1, 2).

## 8. What the kit would need

The kit already has `wasabi` as an optional Install part (`dist/wasabi`: wasabid 0.2, 55,404 bytes, client 76,090;
`dist/Install.installer` page "remote development", key made at install, `KBWASABI` in `tools/kitsize.py`) and amiagent
0.13.2 as a separate option (`dist/net/amiagent-0.13.2`: 88 KB 68000 + 84 KB 68020 builds; Install only copies,
never starts it; `tests/test_dist_installer.py` pins both).
- To put wasabid 0.8 in the kit instead of amiagent: one build (102 KB, compiled for 68000, runs on every CPU; no
  second 020 build), plus the client (165 KB `wasabi` + `wasabi_mcp.py` 13 KB + `wasabi_api.py`, `wasabi_backup.py`,
  `wasabi_fleet.py`, `wasabi_logs.py` ~54 KB for the Mac/NAS side; the Amiga needs none of them).
- Run-time deps: bsdsocket.library 4 (required), input.device, clipboard.device; optional: rexxsyslib 36, keymap 37,
  cybergraphics 40, icon, diskfont, AmiSSL 5 (TLS), mailbox/devicetree resources (Pi health). Key in
  `ENV:wasabi.key` / `ENVARC:`; `plain` argument for LAN clients without TLS keys.
- Build needs the AmiSSL 5.27 SDK (already `vendor/amissl-5.27`) and the extended CGX shim.
- Installer: replace the `AMIAGENT` page text with wasabid's (key, RFC1918-only default, `allow` ranges);
  `kitsize.py` KBAMIAGENT -> the 0.8 files; `tests/test_dist_installer.py` 259-295 and `dist/LICENSES.txt`,
  `dist/README.txt`, Uninstall (`ENVARC:up-term/amiagent`) change with it. Merge it with the existing wasabi option.

## 9. Migration outline per repo (nothing migrated)

1. vtcon tools/rig: add `tools/rig/wasabi_ami.py` exposing the `ami.py` names (`req`-level functions replaced by
   `run`, `get`, `put`, `windows`, `key`, `grab`, `click_px`, `script`) over `wasabi.Conn`; keep `ami.py` until all
   72 importers pass; per script reachability stays "one test per feature". Order: rig.py/wasabi.py/muforce.py
   (use only `req(exec)`), then scripts using only exec/get/put/key/window (about 45), then script/pointer_scale users
   (25 files; need a tick-timed batch or accept CLI drags), then prefs_rig/installer_rig/standalone_rig (grab, click_px).
   Ask upstream for: raw key codes, region grab, tick batch (or write them as a small wasabid patch via
   `wasabi update`).
2. `.mcp.json` and `tools/rig/amimcp.py` -> a `wasabi_mcp` wrapper mapping AMI_HOST/AMI_PORT/AMI_TOKEN to
   WASABI_*; port 1234 + N - 1 per rig (already the rig.py wasabi rule); `make amimcp` -> `make wasabi`.
3. tools/nas: Dockerfile and `mcp.json` swap amimcp for wasabi_mcp.py + client; `skills/amiga-upterm/SKILL.md` text.
4. Kit: section 8.
5. UpRough: `tools/a1200.py` implements the AMI0 frames itself (5 ops) and builds the amiagent kit; replace by
   `wasabi run/put/get/grab` plus a wasabid kit; its 5 serial/tunnel tests call a1200.py functions, so keep the
   function names. Wait until a real-A1200 run with TLS has been done (gap 10).
6. neovim-amiga: 2 scripts import vtcon's ami.py; they follow step 1 with no change of their own.
7. DCTelnet: vendored copies of vtcon tools/rig; refresh with step 1, no own migration.
8. Others: nothing.
