# DOpus lister info/status field above the toolbar (read-only static survey)

D = ~/Code/Reference/dopus5/source (vendor 5.104). A = /Users/spot/Code/UP-Term/vtcon/amarchy. "V" = read in source, "U" = unverified (inferred, not measured on a rig).

## 1. What draws it
The lister top row is four GUI_Elements, not gadgets: name_area (info text, "Reading directory..." / file counts), command_area, parent_area, status_area (SRCE/DEST/OFF, right). Geometry: D/Program/lister_display.c:101-135 (name_area at BorderTop+1, one font row high). The toolbar_area sits below at :138-141 (V).
- Text: select_show_info / lister_set_title in D/Program/lister_title.c ~640-680: pens via lister_title_pens (:379-421: source = ENVCOL_SOURCE fg/bg, dest, or DrawInfo TEXT/BACKGROUND), Move+Text, then RectFill of the leftover box in BgPen (:665, :674). status_text() (D/Program/status_text.c:54-70) only posts LISTER_STATUS to the lister process which ends in lister_status -> lister_set_title (:426-438). V.
- Cleanup fills: lister_clear_title_area RectFill (:692-695) for command/parent/status areas (:289-318). V.
- THE BORDER: lister_refresh (D/Program/lister_display.c:275-279) calls display_gui_border() on name_area, command_area, parent_area, status_area. display_gui_border (D/Program/display.c:927-939) grows the element rect by 1 and calls do3dbox(&gui->rast, &border, 0). do3dbox (D/Program/graphics.c:27-30) is only DrawBox(rp, rect, GUI->draw_info, FALSE) in dopus5.library. Stock pens: SHINEPEN/SHADOWPEN of GUI->draw_info (raised L). No BOOPSI frame, no Move/Draw of its own. V.
- Dual-panel mode (lister_dual_one_window): same idea, headers drawn by lister_dual.c:1496-1497 (RectFill + do3dbox) and :1549 (do3dbox on name_area). V by grep, bodies not read.
- Not this field: title_area (column header buttons, below the toolbar) uses do3dbox at lister_title.c:784/914/1015/1039. The path string gadget at the bottom is dopusstrgclass (separate survey).

## 2. Is each draw call hooked?
- DrawBox (LVO -696): HOOKED. d4_drawbox A/flat.c:959-964, installed via dopus_scan (A/flat.c:2474/2490), gated by dopus version 73.8 + routine checksum (flat_core.c table, per the path-field survey). It calls d4_flat -> d4_flat_pens (A/flat.c:~919-951) -> flat_dopus_decide (A/flat_core.c:~297-311): SKIP only when SHINE pen == BACKGROUND pen (or same RGB), i.e. under the flat pen map; otherwise stock bevel. On SKIP it draws a flat outline with flat_dopus_box_draw (A/flat_glyph.c:529).
- Why a border still shows: flat_dopus_ring(FLAT_EL_DRAWBOX, recessed=0) is false (flat_core.c:~313-316), so the "no ring" branch (flat.c:~935-941) sets st.pen_line = ReadPixel(rp, x0+side, y0+1), i.e. the colour of the pixel just inside the border rect = the element's current fill. The flat code is built to paint a one-pixel frame in the interior colour (made for SRCE/DEST/OFF buttons, comment "DOPUS-BUTTON-NO-RING"). Here the 1 px frame around name_area is drawn in whatever the first interior pixel holds: with the theme source pens (bg = accent, menu_theme.c:85-89 per 2026-11-09-dopus-lister-flat.md) that is the accent colour, so a coloured box shows. Also the sample is read before the area is redrawn (lister_refresh draws borders first, :275-279), so it is stale. Both the "accent" cause and the ordering are U (not measured on a rig); the draw path itself is V.
- RectFill calls (:665, :674, :692): graphics RectFill is hooked (flat_rf_c) but only recolours ring/side/scroller cases from ROM callers; DOpus fills are not ROM, so they pass through in DOpus's own env pens (theme layer). V per 2026-11-09 survey.
- Text: DOpus Text in the area is not a window-title call; flat_tx_c (tx_title) does not touch it. U.
- FieldBox/d4_fieldbody, d4_bevelbody, frameiclass c8_, clone c2_/d5_: not involved (no field box, no BOOPSI image in this row). V by call graph above.

## 3. Same mechanism as the path field?
No. The path field is a dopusstrgclass gadget whose border is DrawFieldBox (FieldBox) plus margin RectFills (button_class.c ~880-975). This row is plain GUI_Element rastport drawing whose border is DrawBox through do3dbox. Both end in the dopus5.library hooks, but the flat decision differs: DrawBox non-recessed takes the "interior-pen frame" branch, FieldBox does not.

## 4. Smallest fix location (hypothesis, UNVERIFIED)
In d4_flat_pens (A/flat.c:~930-945), for FLAT_EL_DRAWBOX with recessed == 0 and a rect that is the 1 px halo of a title area, draw nothing (return 1 with no flat_dopus_box_draw) or, equivalently, make the no-ring branch use the window background pen (flat_state pen_back) rather than ReadPixel. This reuses the existing flat_dopus_decide SKIP path and flat_dopus_ring(). Risk: DrawBox non-recessed is also used for SRCE/DEST/OFF status buttons (which want the interior-pen frame) and toolbar/title headers, so the discriminator must be narrow. DrawBox has no gadget identity; options are rect height == font row + 2 and y within BorderTop..toolbar top (needs window geometry, same method as flat_title_gadget flat_core.c:891-896), or detecting the caller. Measure first: log (rp, rect, ReadPixel) in d4_flat_pens on a rig lister, and check whether the owner's theme `source` pens still give bg = accent.
Alternative in the theme layer (menu_theme.c source/dest pens `3 0` / `2 0`, already proposed in 2026-11-09-dopus-lister-flat.md Fix item 2): it removes the accent-coloured frame because the sampled pixel becomes surface, but leaves a 1 px frame in surface colour, i.e. effectively invisible.

## Accent frame cause (s71 agent 27)

Verdict: none of A, B or C as stated; closest to a fourth cause. The info frame rect DOES reach `d4_flat_pens`, and it takes the RING branch (not the no-ring branch), because the `recessed` argument arrives as a LONG with garbage in the upper word: STATUS showed `rec=570425344` (0x22000000) for the last accent-pen draw. DOpus declares `DrawBox(rp, rect, info, BOOL)` (dopusbase.h:1624, a WORD); the hook reads d0 as a LONG, so any garbage in the upper half makes `recessed ? 1 : 0` true. flat_dopus_ring(DRAWBOX, 1) = 1 -> ring in st.pen_line (the accent) is drawn. The other areas (command, parent, status) show no frame because their d0 upper word happens to be 0 at those calls.

Evidence: diagnostic commits a9d1feaa and 12222b1c on branch dopus-field-no-ring (DIAG; to be reverted). Binary RAM:amarchy-flat 226836 bytes, md5 6e7cd7d616c8eb0908e5462bbb23aaab, resident on rig 68 (make flat-budget rc 0). After one `dopus refresh all` + Wait 1:
`dopus bevel calls=0 face=37 nopix=0 d5=8 DIAG n=11 acc=2 ... ACC el=0 rec=570425344 rect=4,14,286,26 ring=1 fp=0`
- calls=39 per refresh, face=37 (no-ring draws, read pen fp=0 = background, rgb 0x1A1B26), acc=2: exactly two d4 draws end with pen_line == the accent (pen 3): one per lister. The ACC rect 4,14..286,26 is the front lister info frame in window coordinates (screen 186,107..468,119 = window + 182/93). el=0 (DrawBox), ring=1.
- Pixels after the refresh: rear frame (4,14), (100,14), (4,20), (345,20), (100,26) and front (186,107), (300,107), (186,113), (468,113), (300,119) are all #7AA2F7; interior (100,15), (5,15), (5,25) #1A1B26.
- The pre-refresh grab was already accent (frame persisted from the older build's draw); dopus refresh needs `SYS:Rexxc/rx "ADDRESS DOPUS.1; dopus refresh all"`.
- So (A) is wrong: the no-ring branch was never taken for this rect (face counts the other 37 draws; their fp is the background pen). Not (B): no second draw is needed; the ring branch alone paints it. Not (C): it reaches the hook.
Unverified: the actual d0 upper-word garbage in the DOpus caller (not disassembled); the rear lister's ACC rect (only the last accent draw is stored, acc=2 implies one per lister).
Fix proposal (not implemented): in d4_drawbox (and any DrawBox entry) take recessed as the WORD it is (`(WORD)recessed`, or `recessed & 0xFFFF` before d4_flat_pens), and add a pure-function/regression test with an upper-word-garbage value (0x22000000 -> not recessed). Check the FieldBox and Bevel entries: the bevel body takes recessed as ULONG compared == 1, FieldBox passes 0.

## Fix recessed width + rig proof (s71 agent 28)

Cause fix on branch dopus-field-no-ring, commit a417366d (after reverting both DIAG commits as fee61a25 and 2d437c8e; `git diff e8c0dc0c` against the reverted HEAD was empty). L_DrawBox declares BOOL recessed (a WORD, gui.c:27-30) but d4_drawbox read the whole long in d0; DOpus passes 0x22000000 for the raised info-field frame, so the hook took the ring branch. New pure function flat_dopus_recessed(long d0) = (short)d0 != 0 in flat_core.c/.h (searched flat_core.*, flat.c and the other amarchy cores for an existing BOOL/WORD argument normaliser: none), used only for d4_drawbox's own decision; the saved stock routine still gets d0 untouched.
