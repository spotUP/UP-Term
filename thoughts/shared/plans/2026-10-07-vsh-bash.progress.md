## Answers to the P0 open questions (code read, rig not run)

- Does the console honour `TIOCSPGRP`? No packet exists for it. ixemul's `__tioctl.c:597-612` handles
  `TIOCSPGRP`/`TIOCGPGRP` inside the library: it stores/returns `u.u_session->pgrp` and answers 0;
  nothing reaches the vtcon handler (grep of `handler/*.c` for `TIOCSPGRP`/`PGRP`: none). So a program
  that calls `tcsetpgrp` succeeds, with no effect on the terminal. Unconfirmed at run time.
- Is `/dev/fd` available on ixemul-vtcon? No, by reading: `library/open.c` special-cases `/dev/tty`
  (line 111) and `/dev/pty*`/`/dev/tty*` (261); `__plock.c:201-211` `/dev/null` and `/dev/tty`;
  `__open.c:65` sends other `/dev/` names to the filesystem. A grep of the library tree for
  `dev/fd` and `dev/stdin` finds nothing; `mkfifo` is a stub (research bash-port-fork-sites).
  Confirms the plan's temp-file process substitution (V59). Unconfirmed at run time.

No gain: `-s`/debug stripping (the binary has no symbols already: `-x` in the link line), `-Rshort`
(identical size), `-O3`, `-speed`. Signal tables: vsh has ONE table (`sh_signames`; `kill -l` and
`sig_number` share it); `shell/ixkill.c` has a second one but is a separate ixemul gcc program that cannot
share a vbcc object. Option listing is already table-driven (`sh_optab`). So no source-level dedupe of
those was possible; the flags were the real saving. vsh is 92,568: the P1 interim budget (+14 KB = 92,240)
is exceeded by 328 bytes; the overall ~160 KB ceiling stands. Risk: `-O=1` is a less-tested vbcc
configuration and nothing on the host runs the Amiga build: the rig must run the vsh probes once (V33).

Notes on the new code:
- `sh_run_text` now reads input the way bash does, one command at a time (as many lines as it needs),
  executing each before parsing the next. This is what makes `set -v` echo exactly the lines read after it
  (V19), and it also means a syntax error stops a script after the commands before it, and an alias made
  on one line works on the next (both as bash). `sh_parse_text` now reports a text that ends in a
  backslash-newline as incomplete.
- `read`: new flags -d -n -N -p -t -u (0..2) -s -e; line mode unchanged, the others read byte by byte
  through `sh_os.read`; `-t` is per read, not total, through new optional `sh_os.ready` (Amiga:
  `WaitForChar` on an interactive handle, always ready for files and pipes: unconfirmed for pipes);
  `-s` through optional `sh_os.echo` (Amiga: `SetMode` raw, CR ends the line); `-e` is accepted and
  ignored. A last line with no newline now gives status 1 with the variable set (as bash). The Amiga
  byte-wise `Read` after `FGets` on the same handle can lose what the DOS buffer holds: NOT RUN on the rig.
- `printf -v var`, `%q` (backslash style), `--`; `%*d %-*s %.*s %i %u` already worked. `%b` loses NUL
  bytes: documented in `dist/README.txt` "Differences from bash" (probe `builtins/printf_bnul`).
- `local` alone lists the running function's locals (`sh->local_mark`), `local -p` too.
- V32: `tools/bashdiff.py` reads `<probe>.hits` (NAME>=N / NAME=N) and runs the probe under
  `vsh_host --hits`; `options/p1_reach` (flags `-euc`) asserts ERREXIT=1 PIPEFAIL>=1 TEST_BINARY>=1
  INVOKE_CLUSTER=1; checked that a wrong assertion fails the probe.
- `read -t 0` on a pipe is racy against bash (the probe was dropped).

## V67 / V78 partial (host only, 2026-10-07, third pass)

Not ticked (each has an open part). Done and host-verified, `make test` green:
- V67 floats: `printf %f %F %e %E %g %G` (flags, width, precision, `*`, `l L h` modifiers, `'c`, 0x integers,
  inf, nan, rounding half to even, subnormals, "Result too large" and status 1 for out-of-range and
  invalid input) in `shell/sh_float.c`: no libm, no libc float formatting, no double type in vsh at all
  (vbcc's libc cannot be assumed to have it; plan wording "link vbcc's libc" was not needed). The argument is
  read into an IEEE double (53-bit mantissa) with 16-bit-limb integers and printed from its exact value. Checked
  against bash 5.3.9 over 1,300 formats x values (5,232 lines, 0 differences; the random values included),
  precision capped at 400. Open in V67: `%a`, `%(fmt)T`. Behaviour change found: bash reports an empty
  argument ('') of a numeric conversion as "invalid number" (status 1); vsh now does too (`%d` as well).
  Bash here is a double (arm64 macOS); an x86 bash prints long double, so a Linux oracle may differ in the
  last digits of `%.20f`: probes keep to values the double formats exactly or to <= 17 digits.
- V78: `trap` over the 31 signal names (table index = signal number, 0 = EXIT): names with and without
  `SIG`, numbers, `trap -l`, `trap -p [sig...]`, `trap -- action sig`, `trap USR1` (one operand that is a
  signal resets it), listing in bash's `SIGINT` spelling and number order. `kill -SIG $$` runs the trap
  (internal delivery). Open in V78: delivery of a signal sent by ANOTHER process (host: needs sigaction
  handlers in `tests/vsh_host.c`; Amiga: break bits D/E/F and window events), the EXIT trap on a fatal
  signal, n/a-amiga entries.
- kill on the Amiga (`os_signal` in `shell/vsh.c`; COMPILE-ONLY, rig not run): `kill -0 pid`, `kill -s SIG
  pid`, `kill %job`. INT is CTRL_C and QUIT CTRL_E (the bits the console sends, so native commands honour
  them); every other signal goes through ixkill (so only ixemul processes), HUP and TERM falling back to
  CTRL_C; a pid is accepted if it is a job of this shell or a live task (ExecBase task lists); the shell
  itself: INT = Ctrl-C, TERM HUP QUIT KILL end it (128+sig), others ignored.
- Size: `build/amiga/vsh` 99,224 bytes (92,568 before; +6,656: floats, trap table, os_signal).
- `make ratchet-sort` sorts tests/bash/ratchet.txt (byte order), set compared before and after: identical.
