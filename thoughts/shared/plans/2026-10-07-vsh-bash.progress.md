## Answers to the P0 open questions (code read, rig not run)

- Does the console honour `TIOCSPGRP`? No packet exists for it. ixemul's `__tioctl.c:597-612` handles
  `TIOCSPGRP`/`TIOCGPGRP` inside the library: it stores/returns `u.u_session->pgrp` and answers 0;
  nothing reaches the vtcon handler (grep of `handler/*.c` for `TIOCSPGRP`/`PGRP`: none). So a program
  that calls `tcsetpgrp` succeeds, with no effect on the terminal. Unconfirmed at run time.
- Is `/dev/fd` available on ixemul-vtcon? No, by reading: `library/open.c` special-cases `/dev/tty`
  (line 111) and `/dev/pty*`/`/dev/tty*` (261); `__plock.c:201-211` `/dev/null` and `/dev/tty`;
  `__open.c:65` sends other `/dev/` names to the filesystem. A grep of the library tree for
  `dev/fd` and `dev/stdin` finds nothing; `mkfifo` is a stub (research bash-port-fork-sites).
  Confirms the plan's temp-file process substitution (V59). Unconfirmed at run time.

Notes on the new code:
- `sh_run_text` now reads input the way bash does, one command at a time (as many lines as it needs),
  executing each before parsing the next. This is what makes `set -v` echo exactly the lines read after it
  (V19), and it also means a syntax error stops a script after the commands before it, and an alias made
  on one line works on the next (both as bash). `sh_parse_text` now reports a text that ends in a
  backslash-newline as incomplete.
- `read`: new flags -d -n -N -p -t -u (0..2) -s -e; line mode unchanged, the others read byte by byte
  through `sh_os.read`; `-t` is per read, not total, through new optional `sh_os.ready` (Amiga:
  `WaitForChar` on an interactive handle, always ready for files and pipes: unconfirmed for pipes);
  `-s` through optional `sh_os.echo` (Amiga: `SetMode` raw, CR ends the line); `-e` is accepted and
  ignored. A last line with no newline now gives status 1 with the variable set (as bash). The Amiga
  byte-wise `Read` after `FGets` on the same handle can lose what the DOS buffer holds: NOT RUN on the rig.
- `printf -v var`, `%q` (backslash style), `--`; `%*d %-*s %.*s %i %u` already worked. `%b` loses NUL
  bytes: documented in `dist/README.txt` "Differences from bash" (probe `builtins/printf_bnul`).
- `local` alone lists the running function's locals (`sh->local_mark`), `local -p` too.
- V32: `tools/bashdiff.py` reads `<probe>.hits` (NAME>=N / NAME=N) and runs the probe under
  `vsh_host --hits`; `options/p1_reach` (flags `-euc`) asserts ERREXIT=1 PIPEFAIL>=1 TEST_BINARY>=1
  INVOKE_CLUSTER=1; checked that a wrong assertion fails the probe.
- `read -t 0` on a pipe is racy against bash (the probe was dropped).

## V93 design spike (2026-10-08; code read, NOT run on the rig)
Question: how does the handler ask vsh for a completion while vsh waits in a DOS Read?
Read: handler/complete.h (Tab is answered by a worker process through `complete_req`; the shell's words already reach it
as `extra`, pushed by ACTION_VTCON_WORDS, handler/vtcon_packets.h:14), handler/vtcon_handler.c `service_reads`
(2861-2896: a cooked Read is answered from `c->in` when a line is complete; the handler may append any bytes to `c->in`).
Findings:
1. The specs that need no shell code (`complete -W words`, `-f -d -c -a -v`, `-o` options, `compgen` of the same) can be
   evaluated BY THE HANDLER: vsh pushes each command's spec through the WORDS packet (or a new op of
   ACTION_VTCON_HISTORY-style: one packet, `cmd\0flags\0wordlist`) whenever `complete` changes one (sent before the
   next prompt, as sh_hist_config is); the Tab worker picks the spec of the line's first word and answers from the
   word list / file / directory / command / alias / variable sources it already has. No async read needed.
2. `-F function` and `-C command` need the shell: no second port is required. The handler answers vsh's waiting Read
   with a private line (`ESC _ vsh-complete <point> <line> LF`) in `c->in` WITHOUT resetting the line editor;
   `os_read_line` sees the prefix, sets COMP_WORDS/COMP_CWORD/COMP_LINE/COMP_POINT, runs the function in the shell, and
   sends COMPREPLY back with one packet (op COMPLETE_REPLY, NUL-separated words), then calls Read again; the handler
   inserts or lists the words as for any candidates. The Read is synchronous throughout; vsh never waits on two ports.
   Unconfirmed: that the line editor survives a Read completed with a non-edited line (le state is in `c->le`, not in
   the packet), and what a program in raw mode reading the same console would see (the marker is only sent to a
   reader that announced completion support, a flag set by the same config packet as the edit mode).
3. Cost: handler growth (spec table, a marker path in service_reads), vsh growth about 3 KB (complete, compgen,
   compopt builtins, COMP_* variables, the marker handling). Within the P7 +8 KB.
Not built. V93 stays open; V94 (reachability) needs it; V92 (bind/inputrc) is independent of V93 but not started.

## V85 coproc with an external program: analysis before the fix (2026-10-08, rig 2)
- Invariant violated: a pipe Read answers as soon as the pipe holds at least one byte (POSIX read on a pipe).
  vsh's pipes are PIPE: (KS 3.1 L:Queue-Handler). Measured with tests/amiga/pipeprobe (new): 6 bytes written,
  ACTION_READ for 4096 sent: `read 4096: no answer` in 3 s. ixemul is not at fault: its read() on a DOS handle is one
  Read() for the whole length (library/__read.c, normal path). So `coproc cat` (cat reads 4096) never sees a line; every
  vsh pipeline delivers late in the same way (`cmd | while read`), the coproc is where it deadlocks.
- Levels: (1) PIPE: open mode or packet: none; Queue-Handler has no partial-read mode, and a writer cannot make a
  reader's oversized Read return (only by padding data). Out. (2) ixemul pipe() through IXPIPE:: IXPIPE: wraps an fd
  that an ixemul process already owns (ACTION_IXEMUL_MAGIC); vsh is a native program and cannot make one; also IXPIPE:
  is only installed when no other copy exists. Out. (3) A pipe whose handler answers partial reads, owned by this kit.
  pty-handler (PTY:, mounted by the kit and the rig boot) already has exactly that path: slave output goes to a 4 KB
  queue that master_reads answers partially, EOF on the last writer's close, a hung-up writer's data is dropped
  (no deadlock). Picked: a pipe kind in pty-handler, `PTY:<id>/w` (write end, NEWFILE creates, a taken id is refused)
  and `PTY:<id>/r` (read end): the pair without the line discipline, not interactive (isatty 0, no termios packets).
  vsh's os_pipe opens those (falls back to PIPE: when PTY: is not mounted or an older pty-handler refuses the name).
  A separate handler would duplicate pty-handler's process, queue and END code and need a new DOSDriver; a raw pty
  pair would make the coproc's stdin a terminal and cannot close one direction.
- Scope: os_pipe is vsh's one pipe maker, so pipelines, $(...) and coprocs all move to it (the root, not a coproc
  special case). vsh's broken-pipe drain (sh_pipe.h) still works: the drain reads partial data, breaks the writer.
- Done (2026-10-08), V85 ticked with rig evidence. pty-handler: pipe kind (handler/pty_name.h names and open rules,
  pty_handler.c: raw copy into the pair's 4 KB queue, fh_Port 0, read/write on the wrong end refused, no termios).
  vsh os_pipe: `PTY:v<task hex><n hex>/w` NEWFILE then `/r` OLDFILE, the next n on ERROR_OBJECT_IN_USE, PIPE: when PTY:
