# Tabs (T1)

Owner 2026-10-02/03: "we need support for multiple tabs each tab should be able to have it's own
theme and settings", "just like iterm2", "go for tabs". Live prefs (L1) apply per tab.

## Design (lead, decided)

One handler process per tab, all drawing into one Intuition window.

Today every XCON: Open is its own handler process (con) with its own window. A tab is exactly
that process without a window of its own: its shell, DOS stream, engine (vtwin), profile,
menus, completion, KingCON state, watcher (L1) all stay as they are. What changes is who owns
the window and where the events come from.

- **Host**: the process that opened the window (tab 1). It owns the Intuition window and its
  IDCMP. It keeps the tab list, draws the tab bar (only with 2+ tabs, one font row tall, inside
  the window's borders above the text) and routes: keys, mouse, menu picks, resize, refresh,
  activate, the close gadget go to the active tab -- itself, or a message to that tab's
  process. A click on the bar switches tabs.
- **Tab**: a handler process started by `NewShell "XCON:.../TAB <host port>"` (the spec
  parser wants a space after the keyword), FROM a script `FailAt 2147483647 / C:vsh /
  EndCLI` -- without the FailAt vsh's last status (127) failed the script and the tab stayed
  on an AmigaDOS prompt. It finds the
  host's public port, registers, gets the window, and attaches its vtwin to it with a RastPort
  of its own (a copy of the window's, same layer: two processes never share pens or a font)
  and the bar's height as a top inset. Only the active tab draws; the others keep running
  their engines (output still arrives) and draw nothing. Activating a tab redraws it whole and
  puts its menu strip and title on the window.
- **New tab**: UP-Term > New tab (Right Amiga T) in any tab: the host starts the NewShell in a
  worker (DOS). The new tab gets the active tab's profile.
- **Switching**: Right Amiga 1-9 (that tab), Right Amiga . / , (next / previous), the bar,
  UP-Term > Next tab / Previous tab. Not ] / [ as first planned: on the owner's Swedish keymap
  those keys are letters (the rig moved the window on Right Amiga + the [ key's raw code);
  digits have the same raw codes on every keymap.
- **Who draws**: the text area has one owner at a time. Handing it over is a handshake: the
  host sends HIDE to the old tab and shows the new one only when HIDE is answered (the old
  tab has taken its complement cursor away and stopped drawing). Shown at once, the old
  tab's last cursor flip landed on the new tab's pixels (owner 2026-10-03: "the cursor from
  the other tab leaks into the second tab").
- **Closing**: the close gadget and UP-Term > Close tab close the active tab (as the gadget
  closes a window today: EOF to its shell). A tab whose shell ends unregisters and ends; the
  host switches to a neighbour. The host's own shell ending while other tabs live: the host
  keeps the window and its loop, its own session goes (engine freed) -- it is a host only
  until the last tab is gone, then closes the window and ends.
- **Menus per tab**: each tab builds its own strip (its checkmarks: its settings); the active
  tab's strip is the window's. A pick is resolved by the active tab's process.

Why not one process for all tabs: con mixes window and session state in 3700 lines; making
one process serve N sessions means splitting every packet path, and a tab's DOS stream needs
its own process anyway (DOS starts one per Open). One process per tab reuses all of it.

## Checklist

- [x] TB1 renderer: a top inset (the bar) in vr_layout; vtwin: an own RastPort for a shared
      window; a hidden flag (inactive tab: no drawing, still parsing).
- [x] TB2 protocol: host public port; messages REGISTER / UNREGISTER (tab -> host); EVENT,
      ACTIVATE, DEACTIVATE, RESIZE, CLOSE (host -> tab); spec option TAB=<port name>.
- [x] TB3 host: tab list, routing of IDCMP to the active tab, tab bar drawing and clicks,
      NEWSIZE to every tab, the host-only life after its own shell ends.
- [x] TB4 tab side: open = register + attach to the shared window; events from messages;
      menus and title set on activation; unregister on end.
- [x] TB5 commands: New tab (RAmiga T), Next / Previous (RAmiga ] [), Close tab; the new tab
      inherits the profile.
- [x] TB6 rig check (tools/rig/tabs_rig.py): two tabs, each its own shell (output in one does
      not show in the other), switching by key and by click, a profile per tab and L1 updating
      only its tab, closing a tab and the host's own shell, the window ending with the last tab.

## Result (2026-10-03)

6 of 6. tools/rig/tabs_rig.py 19 of 19: new tab (bar, title, own shell), Right Amiga 1/2 and
clicks on the bar, the new tab's profile inherited, L1 per profile (the other profile changing
moves nothing, ours moves the shown and the hidden tab), the close gadget closing only the
active tab, the host's shell ending first, the last tab's shell closing the window.

Not covered by the rig check: the cursor leak (a race; seen by the owner, fixed by the
hand-over handshake, not reproduced on demand). Menus Close tab / Next / Previous run the same
host_command paths as the keys and the gadget; not clicked by the rig.
