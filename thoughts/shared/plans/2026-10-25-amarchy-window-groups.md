# Plan: Window, Workbench and Screens groups for Amarchy

## Goal and finish line

The drawn Amarchy menu gets three root groups: Window (23 rows), Workbench (30 rows), Screens (6 rows), 59 rows in
total, plus 19 Super hotkeys for the rows Omarchy binds to Super keys. Every row either reuses an existing action
kind (`rexx:`, `slash:`) or the one new kind `win:<verb>`, which the Amarchy commodity executes with
intuition.library calls. Done = every checklist item below ticked, with the one reachability test per feature
(section 7) passing on a rig. Partial execution is reported as "n of N open", never "done".

Scope owner approved 2026-10-25 (ledger): all three groups in scope. Not in this plan: Files, Commodities and
Prefs groups, Settings sub-level, tiling rows (research Table A: split, group, layouts, gaps; they stay out).
Size: several agents over several sessions (host work small, the rig phases are the long part).

## Facts the design rests on (read from the code, 2026-10-25)

  `keymap_action_scope` at `config/keymap.c` 119-140. Prefix table `config/keymap.c` 211-215; `action_parse`

- Menu rows: `dist/keymap` `[bind]` begins at line 34 (42 `super+` rows, includes `super+1..9` as one row),

## 1. The action kind win: (K1 to K10)

### 1.1 Grammar in the keymap file

`win:<verb> [argument]`, text after the colon at most 79 characters (`KM_ARG`).

| Verb and arguments | Meaning |
|---|---|
| `win:cycle next` / `win:cycle prev` | activate and bring to front the next or previous window on the target window's screen |
| `win:front` / `win:back` | WindowToFront / WindowToBack of the target window |
| `win:zip` | ZipWindow (toggle between the normal and the zoom box) |
| `win:fullwidth` | ChangeWindowBox to left 0 and the screen's width, top and height kept |
| `win:fullscreen` | ChangeWindowBox to the screen's usable area (below the title bar) |
| `win:save` / `win:restore` | remember or restore the target's box (per window, kept in the commodity, at most 8 windows, oldest dropped) |
| `win:move <left\|right\|up\|down> [pixels]` | MoveWindow by the step, default 32 pixels, clamped on the screen |
| `win:size <left\|right\|up\|down> [pixels]` | SizeWindow: `left` and `up` shrink width and height, `right` and `down` grow them; default 32; never below the window's MinWidth/MinHeight, never beyond MaxWidth/MaxHeight or the screen |
| `win:focus <left\|right\|up\|down\|next\|prev>` | ActivateWindow on the nearest window in that direction (geometry search over the screen's window list), `next` and `prev` as cycle without raising |
| `win:closedrawers` | close every open Workbench drawer window through workbench.library (WBCTRLA_GetOpenDrawerList, CloseWorkbenchObjectA): the Omarchy "close all windows" for drawers only |
| `win:screen <next\|prev\|workbench\|back>` | ScreenToBack of the front screen (`next`, brings the one behind to front); ScreenToFront of the last screen in the list (`prev`); ScreenToFront of the Workbench public screen (`workbench`); ScreenToBack of the front screen (`back`) |
| `win:title <toggle\|show\|hide>` | ShowTitle on the target's screen (Omarchy toggle top bar) |

Closed verb set. No verb closes a foreign window (section 5).

- K4: `amarchy/leaf_core.c` `lf_plan`: `KA_WIN` returns a new plan `LF_WIN` (`amarchy/leaf.h` 24-31).

### 1.3 Execution in the commodity

New files, both listed in the Makefile source lists (this session may append them): `amarchy/win_core.c` and
`win_core.h` (pure, host-tested: verb parse into a struct, all geometry arithmetic, direction search over an
array of boxes, clamp, step) and `amarchy/win.c` (the OS calls). `do_row` (`amarchy/amarchy.c` 165) gets
`case KA_WIN: ok = act_win(b->arg); break;`. Rule from the research: only the commodity task calls these; the
terminal handler never does.

- K5, active-window lookup: `act_win` takes `LockIBase(0)`, reads `IntuitionBase->ActiveWindow`, and checks that
  the pointer is still a member of some screen's window list by walking `Screen->FirstWindow` for every screen
  (never trust a stored pointer). It copies out the box (`LeftEdge`, `TopEdge`, `Width`, `Height`, `MinWidth`,
  `MinHeight`, `MaxWidth`, `MaxHeight`, `WScreen`, the zoom box) into a plain struct for `win_core.c`.
  The target is never an Amarchy window (menu, viewer, gui): skip a window whose title is the Amarchy menu
  window's, or better, whose `UserPort` belongs to a task started by Amarchy (the commodity knows its launched
  tasks through `amarchy/wblaunch.c`; read that file before choosing; decision in the checklist K5).
- K5a, target after the menu opened: the drawn menu is an Intuition window and becomes the active window, so
  `ActiveWindow` is the menu, not the program the owner meant. The commodity therefore records the target at the
  moment it launches the menu or the viewer (`act_menu_kind`, `amarchy/amarchy.c` 100): the window pointer,
  verified as above, stored as a "target ticket" (pointer plus its box). A `win:` row run from the menu uses the
  ticket if the pointer is still found in a window list and its box is unchanged, otherwise the verb fails with
  DisplayBeep and nothing else. A `win:` hotkey (no menu) reads the live ActiveWindow. The ticket is cleared
  when the menu window closes.
- K6, lock discipline per verb (research, section "Window-call safety"):
  - Held under LockIBase, because they only queue a request to Intuition and must not see the window die:
    MoveWindow, SizeWindow, ChangeWindowBox, ZipWindow, WindowToFront, WindowToBack.
  - After UnlockIBase (they take the lock themselves or act on a screen): ActivateWindow, ScreenToFront,
    ScreenToBack, ShowTitle, LockPubScreen/UnlockPubScreen, and every workbench.library call
    (WorkbenchControlA, CloseWorkbenchObjectA) used by `win:closedrawers`.
  - Never called: CloseWindow on any window that is not the commodity's own (research: unsafe, the owner holds
    the IDCMP port).
  - UNVERIFIED and measured in phase K-rig: the nesting of LockIBase with the internal locking of the queued
    calls. If one deadlocks on the rig, that verb moves to the "after unlock" list and revalidates the pointer
    by a second short lock.
- K7, a verb the handler must do instead: none. Everything the terminal's own window needs already exists
  as a kind the handler resolves: own tab close `tab:close`, own window close `menuid:MENU_CLOSE`
  (`super+w`, `super+q` in `dist/keymap`), own full screen `slash:/screen own`, own font `menuid:MENU_FONT_*`. The
  `win:` rows act on whatever window is active, including an UP-Term window, which is only another Intuition
  window to them.
- K8, menu path: `LF_WIN` in `amarchy/leaf.c` (line 174 switch) cannot call Intuition on the owner's behalf in
  a useful way (amarchy-gui is a different task and its own window is active). It sends the row's text to the
  commodity through the existing ARexx port AMARCHY with a new command `WIN <verb and arguments>` handled in
  `rexx_serve` (`amarchy/amarchy.c` 215, next to RUN), which calls the same `act_win`. One implementation,
  two entry points (hotkey through `do_row`, menu through the port). If the port is absent (commodity not
  running) the leaf reports the failure through the menu's normal error line.
- K9, counter: `status_text` (the STATUS reply) gets `wins=<n>`, incremented once per executed `win:` verb
  (not per refused one). It is the sentinel of section 7.
- K10, commodity filter: `win:` hotkeys use the same `cx_install` filter path as other rows; no new
  commodities code is expected. Confirm by reading `amarchy/cx.c` before K5 (it filters on the row table).
