# Every Prefs setting as a row in the Amarchy menu

## Goal

Owner wish (2026-10-26): every UP-Term Prefs setting is a row in the Amarchy menu, Omarchy style, and a
change applies at once. UP-Term Prefs stays as the companion window with the same settings. One table is the
single source of truth for what a setting is (key, kind, values, default, label, help, page, store).

## Owner decisions

- D1 Settings that are not one row (16-colour palette, colour swatches, fonts, screen mode, profiles, Theme)
  get a row that opens a picker: a colour list for swatches and palette entries, the ASL font requester for
  fonts, the ASL screen mode requester for the screen mode, a list for profiles and themes.
- D2 Rows show the current value in the label, for example "Cursor blinks: On". The label is built when the
  menu level opens, in both the drawn menu (amarchy-gui) and the text menu (amarchy-menu).
- D3 Grouping is the same pages as Prefs: Settings > General / Colors / Palette / Keyboard / Advanced /
  Amarchy. One table drives the menu groups and the Prefs pages.
- D4 A menu row writes ENV: and ENVARC: (like Prefs Save): applies at once and survives a reboot.
- D5 Rows edit the active profile; a Profile row switches it, and every row then shows that profile.

## Why a new table

`pg_items[]` (prefs/prefs_ui.c:11-251) is a layout table: id, page, kind, label, grid slot. It holds no key,
default or value list. Those live in three other places: `prefs_fields` (prefs_core.h:25-65), the parse
(prefs_core.c ~60-125), the serialise (prefs_core.c:705-800), and the cycle text arrays in upprefs.c. A menu
that reads any one of these copies would be a fourth copy. The Amarchy keys already have a name plus default
table (`am_keys[]`, amarchy/amconf_keys.c), the precedent to extend.

## Design

### The settings table (one source of truth)

New pure module `prefs/settings_def.c/.h` (no OS calls, host-tested), one entry per setting:

- `id` (enum, stable), `key` (file key, for example `cursor-blink`), `page` (PG_PAGE_*), `kind`
  (SD_CHECK, SD_CYCLE, SD_INT, SD_STRING, SD_COLOUR, SD_FONT, SD_SCREENMODE, SD_PALETTE, SD_THEME,
  SD_PROFILE), `label` (full English words, `_` shortcut kept for Prefs), `help`, `values` (for cycles: file
  value plus display text, for example `{"underline","Underline"}`), `def`, `store` (SD_UPTERM profile or
  SD_AMARCHY file), `get`/`set` on `prefs_fields` or `am_prefs` (offset plus small typed accessor, no
  per-setting code where an offset does).
- Range data for SD_INT (scrollback 1-99999 and its "No scrollback" check stay one setting with a 0 value).
- prefs_core parse and serialise walk the table instead of hand-written per-key lines. The existing
  prefs_core tests are the oracle: the file text before and after the change must be byte-identical
  for the default profile and for the owner's A1200 file (copy pulled from ENVARC:up-term/up-term).
- upprefs cycle text arrays are removed; the gadget builder takes cycle labels from `values`.
- `pg_items` keeps layout only and gains a `setting` id column instead of repeating label and kind
  (label and help come from the table).
- amconf: `am_keys[]` becomes the SD_AMARCHY rows of the same table (or is generated from it); amconf keeps
  its own file and parser.

### Menu rows

- A new synthesised row kind `MN_ROW_SETTING` (like `MN_ROW_INDEX`, menu_core.h), generated by
  `mn_children` when the node is a settings page group. The keymap [menu] keeps one line per page group
  (`settings.general = General | settings:general` and so on), so dist/keymap holds no second copy of the
  labels and the 128-row keymap limit is not touched.
- Label at build time: `sd_row_label(def, fields, buf)` gives "Label: Value" (pure, host-tested, same
  function for both menus). Width: label plus value must fit the menu column; the text menu truncates the
  value, not the label.
- New leaf kind `LF_SETTING` in amarchy/leaf.c:
  - SD_CHECK: toggle. SD_CYCLE: a submenu of the values with the current one marked (one keypress to pick,
    and Enter on the row itself steps to the next value).
  - SD_INT / SD_STRING: the existing `ask_value` prompt, prefilled with the current value; validated by the
    same range check Prefs uses (moved into settings_def).
  - SD_COLOUR / SD_PALETTE: a picker level: the 16 palette entries as rows with their hex, plus "Custom..."
    (ask_value, hex). The drawn menu shows a colour chip per row; the text menu shows the hex.
  - SD_FONT / SD_SCREENMODE: the ASL requester, opened by the menu process on the Workbench screen
    (amarchy-gui and amarchy-menu link prefs_asl.c's picker, not upprefs.c).
  - SD_THEME: list of ENVARC:up-term/themes, apply through `prefs_apply_theme`.
  - SD_PROFILE: list of profiles plus New / Rename / Delete rows (ask_value for names).
- After a set: write through `prefs_save_at` (SD_UPTERM) or `amconf_save_with` (SD_AMARCHY). The existing
  file notifies (vtcon-handler StartNotify, Amarchy reload) apply the change; no new IPC. The menu level
  re-renders with the new value.
- amarchy-menu links prefs_core, prefs_dos, upconf, upconf_rows, amconf, settings_def (no size budget).

### Concurrency with Prefs

Prefs holds one copy of the fields per session (found in 5270f4ba). When the menu writes while Prefs is
open, a later Prefs Save overwrites it. Fix in this plan: Prefs listens to the same file notify and reloads
the fields of pages the user has not edited; edited pages keep the user's edits (no silent loss either way).
